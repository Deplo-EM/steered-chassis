## 2. 已经证明过的事情（可复现）

| 证据 | 怎么复现 | 结果 |
|---|---|---|
| 底盘固件可编译链接 | 首次先按 README 配置，再运行 `cmake --build Chassis/build/verify` | 核对退出码、警告和内存占用；历史结果见`docs/15`，2026-11-11运行代码修复见`docs/19` |
| 云台固件可编译链接 | 首次先按 README 配置，再运行 `cmake --build Gimbal/build/verify` | 同上；本轮已修正Flash构造表只读属性，readelf确认代码LOAD为R E、数据为RW |
| 主机回归检查 | `./tests/run_tests.ps1` | 核对每组失败数与脚本退出码，检查数以本次输出为准 |

单元测试覆盖的具体内容：

- **PID**：比例项、输出限幅、积分限幅、抗积分饱和、reset、微分项。
- **协议**：C2G/G2C 双向「编码→解码」还原、CRC 拦截篡改帧、初始必判离线、两板帧 ID 互补。
- **逆解**：纯前进、原地旋转、云台向左转 90° 后推前进（车往左平移）、等效解翻转、
  舵角速率限幅、零指令保持舵角、轮速限幅。
- **闭环仿真**：跟随模式从 0.5rad 误差出发 3 秒内收敛且不发散（符号正确性）；
  小陀螺底盘转一圈，车体系速度随之旋转、世界方向不变。
- **角度**：`WrapPi` 边界，359° 与 1° 差值为 +2°。

本轮增加的实际达妙/BMI088/CAN驱动与任务集成测试见 `docs/15`。即使编译了真实状态机与通信任务，
主机环境仍替代了 HAL、物理传感器和电机反馈；不能据此宣称所有状态、所有故障或实车性能均已覆盖。

## 4. 验收演示脚本（照着做）

| 步骤 | 操作 | 预期现象 | 对应考核项 |
|---|---|---|---|
| 1 | 两板上电，遥控器先开，所有反馈正常 | 标定和两板各自恢复自检完成后进入 Working；记录实际时长，舵轮静止时保持原位 | 状态机 |
| 2 | 左拨杆打到中（跟随），轻推左摇杆向前 | 车沿**枪口方向**前进 | 跟随 |
| 3 | 保持小幅前进，用右摇杆小幅转动云台；禁止手拨带电云台 | 车头朝云台方向追齐；前进方向随云台朝向改变 | 3.2 坐标约定 |
| 4 | 左拨杆打上（分离），推杆 | 车沿**枪口方向**平移，但车头**不跟着转**（云台独立） | 分离 |
| 5 | 左拨杆打下（小陀螺），拨轮给一点 | 车原地自旋，同时推杆能沿枪口方向平移 | 小陀螺 |
| 6 | 右拨杆打到最下（急停） | 有效急停帧被控制周期采纳后，软件请求全电机零输出；实际卸力与停转按 T6 测量 | 急停（硬性） |
| 7 | 关掉遥控器 | 遥控新鲜度到期后撤销许可并停止喂狗，随后 IWDG 复位；记录总耗时与电机行为 | 看门狗（硬性） |
| 8 | 拔掉两板之间的 CAN 线 | 超过 100ms 无有效新帧后退出 Working；实际停机另测，零帧可能无法送达 | 双板互保 |
| 9 | 重新连调试器，看全局变量 `g_reset_by_iwdg` | 为 `true`，证明刚才那次确实是**看门狗复位**（而不是掉电/复位键） | 看门狗证据 |
| 10 | （可选反证）把 `kDebugAlwaysFeedWatchdog` 临时改成 `true` 重烧，再关遥控器 | 板子**不**复位——说明第 7 步的复位确实是"没喂狗"造成的 | 看门狗演示 |

> **第 9 步的原理**：`MainTaskInit()` 一开始会读 RCC 的 `IWDGRST` 标志并清掉，
> 结果存在全局变量 `g_reset_by_iwdg` 里。复位后重新连上调试器读它，就能直接
> 区分"看门狗复位"和"上电/按复位键"。
>
> ⚠️ **注意方向别搞反**（审计 F2 指出过这个错误）：
> - `kDebugAlwaysFeedWatchdog = false`（默认）= 正常模式，**条件喂狗**，关遥控器会复位；
> - `kDebugAlwaysFeedWatchdog = true` = 调试模式，**无条件喂狗**，板子不会复位。
>
> 调试模式只用于台架上连着调试器、不想接遥控器的场景，**绝不能上车**，验收前必须改回 `false`。

## 5. 已知取舍（验收时可能被问到）

1. **为什么 yaw 下发角速度而不是角度？** → `docs/03` 第 3 节。
2. **为什么云台不用达妙内置位置环？** → `docs/04` 第 5 节。
3. **为什么静止时不把舵轮回正？** → `README.md` 第 6 节。
4. **为什么底盘板要求云台板先 Working？** → 枪口乱晃时不允许开车（`robot.cpp`）。
5. **为什么两板都实现DBUS接收？** → 接收机可在云台，原始18字节通过0x212～0x214转发到底盘；底盘本地接收也保留。
   来源选定必须先收到该来源的有效急停；不得用心跳里的在线标志代替摇杆数据，也不能运动中无确认切换来源。
   云台接收时底盘本地DBUS计数为0可以正常；转发必须完整、新鲜并通过原DT7校验，重复/缺片不续命。
6. **CAN 总线负载会不会太高？** → 必须按整条互联总线统计两板发送、反馈、位填充与重发，
   用分析仪测实际占用、延迟和错误帧。不能仅凭“约 70%”判定可用；调整帧率后要重跑离线、
   发送故障保护与急停时序测试。

### 本轮新增回归范围

统一入口 `tests/run_tests.ps1` 顺序运行原算法/DBUS组、真实Chassis+PID参数组、两板真实Imu封装组、

测试使用替身的层次和数量见 `docs/15`；并未执行硬件故障注入。
