# 08 · 台架故障注入清单

> 现场调试默认沿用Ozone，连接方式与变量窗口见`docs/12`。本文的接口名如`lifeState()`描述代码含义，不应当作Watch中执行目标函数的指令；优先展开真实对象字段。T1复位验证时保持程序运行，不能用Halt代替卡死注入。

> 审计反复强调一句话：**静态审查 + 编译 + 主机测试，不能替代台架上的故障注入。**
> 这份清单把「该验证什么、怎么注入、看哪个变量、什么算通过」全部写成可执行的步骤，
> 验收时照着做，逐项记录结果。

---

## 0. ⚠️ 先读：安全边界

| 规则 | 说明 |
|---|---|
| **只允许轮子架空的台架** | 每一项注入都可能让控制失效，落地绝对不能做 |
| **带注入的固件不能上车** | 测完必须把 `kEnableFaultInjection` 改回 `false` 重新烧录 |
| **提交前查一次开关** | 只查**源码里的开关本身**（不要 `grep -r`，文档里本来就会出现这串字符）：<br>`Select-String -Path RobotComponents\component\fault_injection.hpp -Pattern "kEnableFaultInjection = true"`<br>必须**无结果** |
| 电池满电 | 复位频繁，电压低会干扰观察 |

## 1. 准备

### 1.1 打开注入开关

`RobotComponents/component/fault_injection.hpp`：

```cpp
constexpr bool kEnableFaultInjection = false;   // ← 改成 true
```

重新编译烧录两板；首次配置或新增.cpp后重新configure，仅修改已有头文件开关通常直接build即可。

> ⚠️ **坑**：新增的 `.cpp` 文件靠 CMake 的 `GLOB` 收集，而 `GLOB` 在 **configure** 时才求值。
> 如果你刚拉下代码第一次编译，先跑一次：
> ```powershell
> cmake -S . -B build/verify -G Ninja -DCMAKE_BUILD_TYPE=Debug
> ```
> 否则会报 `undefined reference to robot::g_fault_id`。

### 1.2 在调试器里切换故障项

上电后默认 `robot::g_fault_id = 0`（不注入）。在调试器的 **Watch / Expressions**
窗口里直接改写它，不用重烧：

| 值 | 含义 |
|---|---|
| 0 | 不注入（默认） |
| 1 | 控制任务死循环 |
| 2 | DBUS 拨轮改成 0xFC00 |
| 3 | 冻结 IMU 采样 |
| 4 | 占满 CAN 发送邮箱 |

### 1.3 要观察的变量（都在调试器里）

> **为什么这些变量一定存在**：`g_fault_id` / `g_fault_injection_enabled` 是
> `volatile` 全局变量，并且 `MainTaskInit()` 启动时会对它们做一次普通写。
> volatile 访问是编译器不能消除的副作用，所以即使总开关关闭、注入代码全被优化掉，
> 这两个符号也会保留在 ELF 里（可核实：`arm-none-eabi-nm 固件.elf | findstr g_fault`）。
>
> 之前踩过两个坑：只用 `__attribute__((used))` 不够（只管编译器，链接器
> `--gc-sections` 照样回收）；`__attribute__((retain))` 在本工具链下**被忽略**
> （编译会报 `'retain' attribute ignored`，所以没有采用）。最终靠
> "volatile + 启动时写一次"解决，并已用 `nm` 逐板确认。
>
> ⚠️ **`nm` 只证明符号存在，不能证明开关是 false**——带注入的固件也有这两个符号。
> 想离线确认"这个 .elf 是安全版"，看下面的构建标签。

| 变量 | 含义 | 正常值 |
|---|---|---|
| `robot::g_fault_injection_enabled` | 当前固件是否带注入能力（运行时值） | 测完应为 `false` |
| `robot::g_build_tag` / `g_build_tag_addr` | 构建标签：`SAFE-BUILD` / `FAULT-INJECTION-BUILD` | 指向 `SAFE-BUILD` |
| `robot::diag::g_cpu.cycle_count` | 控制周期计数 | 持续增长 |
| `robot::diag::g_cpu.cycle_ticks_max` | 单周期最大耗时（tick，84 tick = 1µs） | < 84000（1ms） |
| `robot::diag::g_cpu.overrun_count` | 超时次数 | 0 |
| `g_reset_by_iwdg` | 本次复位是不是看门狗触发的 | 正常上电为 `false` |
| `s_dbus_valid_frames` / `s_dbus_invalid_frames` | 合法 / 非法 DBUS 帧计数（`comm_task.cpp` 内静态变量） | 非法为 0 |
| `s_can_tx_fail_count` | CAN 发送失败次数 | 0 |
| `state_`（用docs/audit_evidence/field_read.gdb读真实对象） | 0 Dead / 1 Resurrection / 2 Working | 2 |
| `$imu->healthy_` / `bad_samples_total_`（同脚本） | IMU 数据是否可信 / 累计异常样本 | true / 0 |
| `$peer->rx_ok_count_` / `rx_error_count_`（同脚本） | 双板帧成功 / CRC 错误数 | 错误为 0 |

## 2. 注入项

> 上电先保持有效遥控急停完成确认，完整流程见 `docs/06`。所有物理停机时间均需实测。

### T1 · 控制循环卡死 → 看门狗必须复位

| 项 | 内容 |
|---|---|
| **目的** | 验证审计 H1 的修复：喂狗只发生在控制周期末尾，控制卡死时一定会复位 |
| **注入** | `g_fault_id = 1` |
| **做法** | 让程序继续跑；测量复位并核对RCC复位原因；调试连接断开还可能是供电或通信问题 |
| **观察** | ① 测量复位时刻（调试器是否断开不能独立证明复位）；② 重新连接后 `g_reset_by_iwdg == true`；③ `diag::g_cpu.cycle_count` 归零重新计数 |
| **通过标准** | 200ms 左右复位，且复位原因确实是 IWDG |
| **注意** | 注入点**故意不关中断**——UART/CAN 中断还在跑。这正是"中断还活着但控制死了"的场景 |
| **记录** | 复位耗时 ______ ms；`g_reset_by_iwdg` = ______ |

### T2 · 非法 DBUS 帧（0xFC00 拨轮）→ 不得授权输出

| 项 | 内容 |
|---|---|
| **目的** | 验证审计 H2/F1：校验器与解码器位宽一致，脏数据不会被当成有效指令 |
| **注入** | `g_fault_id = 2` |
| **做法** | 遥控器保持开机；把每帧 DBUS 的拨轮字节改成 0xFC00（低 11 位仍是 1024） |
| **观察** | ① `s_dbus_invalid_frames` 持续增长，`s_dbus_valid_frames` 不再增长；② `lifeState()` 在 100ms 内回到 0（Dead）；③ 车**没有任何动作**；④ 接着看门狗在约 200ms 复位（没有合法帧就不喂狗） |
| **通过标准** | 车不动 + 进入 Dead + 最终复位 |
| **反证** | 把 `kEnableFaultInjection` 关掉、手动构造一帧脏数据，会发现修正前的版本会算出 `rc_wheel≈96`（见 `tests/test_main.cpp` 的对拍用例） |
| **记录** | 进入 Dead 用时 ______ ms；车是否动作：______ |

### T3 · IMU采样停更/传输失败 → 撤销输出资格

| 项 | 内容 |
|---|---|
| 目的 | 验证跳过采样、SPI错误、设备时钟/DRDY停止更新不会无限沿用合理旧值 |
| 注入 | `g_fault_id=3`跳过Imu::update；它只覆盖应用样本过期，不等于模拟SPI或传感器内部冻结 |
| 做法 | 固定架空台架、准备切断驱动电源；Working后注入，不手动转动带电云台 |
| 观察 | `$imu->last_sample_tick_`不再更新；`uwTick-last_sample_tick_`超过20ms后，下一控制周期退出Working、输入清零；`healthy_`可能仍为true，不能单看它 |
| 通过标准 | 从最后有效样本起超过20ms后，下一控制周期软件停机；同时测量实际卸力时间。取消注入后按有效急停确认并经过自检，不得正常档自行恢复底盘 |
| 补充台架 | SPI超时/断线、设备时钟不动、加速度或陀螺DRDY不更新分别验证。传输失败当次样本无效；时钟/DRDY超时≤20ms窗口；重置设备后需重新标定 |
| 边界 | 静止时数值相同而时钟/DRDY推进是正常情况，不能误判；若内部异常仍伪造合理数据及新鲜度，需独立参考验证 |
| 记录 | 注入类型 ___；最后样本至Dead ___ ms；实际卸力 ___ ms；恢复确认 ___ |

### T4 · CAN 发送失败 → 清零、锁存、停喂狗与人工恢复

| 项 | 内容 |
|---|---|
| 注入 | 架空且准备断驱动电源，`g_fault_id=4`；若未实际造成发送失败，调整测试条件并记录，不能判通过 |
| 软件观察 | `canTxFailedCycles()`、`canTxHealthy()`、`lifeState()`、电机 `getInput()`、`canFeedWatchdog()`；原 `s_can_tx_fail_count` 仅统计入邮箱失败 |
| 首次失败 | 已完成邮箱无TXOK或2ms未完成也判失败；撤销待发队列并确认邮箱空，Dead清零；后续尝试零指令，正常档不能清锁存 |
| 持续失败 | 连续 10 ms 失败后不喂狗；测量随后的 IWDG 复位和 `g_reset_by_iwdg` |
| 恢复 | 取消注入后保持正常档应仍无输出；有效急停且连续 100 ms 提交、已完成邮箱TXOK及停机取消监督全部通过才解除锁存，再经过自检；复位后同样需上电急停确认 |
| 额外注入 | 除邮箱占满外，还需无ACK、发送错误、停机时仍有非零帧排队；用总线分析仪核对无延后旧命令。本版硬件自动重发关闭；ACK不等于目标电机执行 |
| 物理通过条件 | 同时测电机电流/动作和电机自身通信失联行为；HAL 接受报文不等于送达，清零可能发不出去 |
| 记录 | 首次失败至清零 ___ ms；停喂狗 ___ ms；复位 ___ ms；实际卸力 ___ ms；恢复条件 ___ |

### T5 · 1ms 周期最坏耗时（不需要注入）

| 项 | 内容 |
|---|---|
| **目的** | 证明"设计 1ms"真的跑得完 |
| **做法** | 正常上电，遥控器开，让车进 Working；分别静止 / 推满杆 / 小陀螺各跑 30 秒 |
| **观察** | `diag::g_cpu.cycle_ticks_max`、`cycle_ticks_avg`、`overrun_count` |
| **换算** | `cycle_ticks_max / 84` = 微秒 |
| **通过标准** | `overrun_count == 0`，且 `cycle_ticks_max` 明显小于 84000（建议 < 50%） |
| **记录** | max = ______ µs；avg = ______ µs；overrun = ______ |

### T6 · 急停响应（示波器 / 逻辑分析仪）

| 项 | 内容 |
|---|---|
| **目的** | 拿到端到端的急停延迟数字 |
| **做法** | 探头 1：DBUS 信号线（最后一帧拨杆变化）；探头 2：CAN_H/CAN_L 或电机电流 |
| **延迟构成** | 遥控器帧周期（0~10ms，等下一帧）+ 控制周期（≤1ms）+ CAN 发送（约 0.1ms） |
| **通过标准** | 总延迟 ≤ 12ms；软件侧 ≤ 1 个控制周期 |
| **记录** | 实测 ______ ms |

### T7 · 掉线与双板互保（不需要注入）

| 项 | 内容 |
|---|---|
| **做法** | ① 关遥控器 → 记录两板复位；② 断双板 CAN → 记录离线判定、软件清零与实际停机 |
| **观察** | `lifeState()`、`isOffline()`、电机输出 |
| **通过标准** | 在线阈值到期后退出 Working；另行确认电机实际卸力，不能仅看软件变量 |
| **记录** | 停机用时 ______ ms |

### T8 · 复位原因核对（配合 T1/T2）

| 项 | 内容 |
|---|---|
| **做法** | 正常上电（按复位键）→ 读 `g_reset_by_iwdg` 应为 `false`；再跑 T1 → 应为 `true` |
| **意义** | 证明 `g_reset_by_iwdg` 确实能区分"看门狗复位"和"手动复位"，T1 的结论才成立 |
| **记录** | 手动复位 = ______；看门狗复位 = ______ |

## 4. 测完的收尾（必做）

1. `fault_injection.hpp` 里 `kEnableFaultInjection` 改回 **`false`**；
2. 重新编译、烧录两板；
3. 确认烧进去的是**安全固件**。三种检查能证明的东西不一样，别混用：

   | 检查 | 能证明什么 | 怎么查 |
   |---|---|---|
   | **构建标签（离线，推荐）** | 这个固件文件**是按开关 false 编出来的** | `arm-none-eabi-strings 固件.elf \| findstr BUILD` → 只应出现 `SAFE-BUILD`；若出现 `FAULT-INJECTION-BUILD` 说明烧错版本 |
   | **调试器读值（在线）** | 芯片里**当前运行**的固件，其运行时标志为 false | 读 `robot::g_fault_injection_enabled`，应为 `false` |
   | ~~`nm` 查符号~~ | 只证明符号存在，**两种固件都有** | 不能单独用来判断开关状态 |

   > 判别力已实测：把开关改成 `true` 重新编译，标签变成 `FAULT-INJECTION-BUILD`；
   > 改回 `false` 又变回 `SAFE-BUILD`。
4. 跑一遍主机测试：`./tests/run_tests.ps1`（各组失败数为 0、总脚本退出码为 0；检查数以输出为准）；
5. 提交前只查开关本身（不要 `grep -r`，文档里会出现这个字符串）：
   ```powershell
   Select-String -Path RobotComponents\component\fault_injection.hpp -Pattern "kEnableFaultInjection = true"
   ```
   必须**无结果**。
