# 08 · 台架故障注入清单

> 审计反复强调一句话：**静态审查 + 编译 + 主机测试，不能替代台架上的故障注入。**
> 这份清单把「该验证什么、怎么注入、看哪个变量、什么算通过」全部写成可执行的步骤，
> 验收时照着做，逐项记录结果。

---

## 0. ⚠️ 先读：安全边界

| 规则 | 说明 |
|---|---|
| **只允许轮子架空的台架** | 每一项注入都可能让控制失效，落地绝对不能做 |
| **带注入的固件不能上车** | 测完必须把 `kEnableFaultInjection` 改回 `false` 重新烧录 |
| **提交前 grep 一次** | `grep -r "kEnableFaultInjection = true"` 必须无结果 |
| 电池满电 | 复位频繁，电压低会干扰观察 |

---

## 1. 准备

### 1.1 打开注入开关

`RobotComponents/component/fault_injection.hpp`：

```cpp
constexpr bool kEnableFaultInjection = false;   // ← 改成 true
```

重新编译烧录两板（**必须重新 configure**，见下面的坑）。

> ⚠️ **坑**：新增的 `.cpp` 文件靠 CMake 的 `GLOB` 收集，而 `GLOB` 在 **configure** 时才求值。
> 如果你刚拉下代码第一次编译，先跑一次：
> ```powershell
> cmake -S . -B build/verify -G Ninja -DCMAKE_BUILD_TYPE=Debug
> ```
> 否则会报 `undefined reference to robot::g_fault_id`。

### 1.2 在调试器里切换故障项

上电后默认 `robot::g_fault_id = 0`（不注入）。在调试器的 **Watch / Expressions**
窗口里直接改写它，不用重烧：

| 值 | 含义 |
|---|---|
| 0 | 不注入（默认） |
| 1 | 控制任务死循环 |
| 2 | DBUS 拨轮改成 0xFC00 |
| 3 | 冻结 IMU 采样 |
| 4 | 占满 CAN 发送邮箱 |

### 1.3 要观察的变量（都在调试器里）

| 变量 | 含义 | 正常值 |
|---|---|---|
| `robot::g_fault_injection_enabled` | 当前固件是否带注入能力 | 测完应为 `false` |
| `robot::diag::g_cpu.cycle_count` | 控制周期计数 | 持续增长 |
| `robot::diag::g_cpu.cycle_ticks_max` | 单周期最大耗时（tick，84 tick = 1µs） | < 84000（1ms） |
| `robot::diag::g_cpu.overrun_count` | 超时次数 | 0 |
| `g_reset_by_iwdg` | 本次复位是不是看门狗触发的 | 正常上电为 `false` |
| `s_dbus_valid_frames` / `s_dbus_invalid_frames` | 合法 / 非法 DBUS 帧计数（`comm_task.cpp` 内静态变量） | 非法为 0 |
| `s_can_tx_fail_count` | CAN 发送失败次数 | 0 |
| `GetRobot()->lifeState()` | 0 Dead / 1 Resurrection / 2 Working | 2 |
| `GetImu()->isHealthy()` / `badSamples()` | IMU 数据是否可信 / 累计异常样本 | true / 0 |
| `GetGimbalChassisComm()->rx_ok_count()` / `rx_error_count()` | 双板帧成功 / CRC 错误数 | 错误为 0 |

## 2. 注入项

### T1 · 控制循环卡死 → 看门狗必须复位

| 项 | 内容 |
|---|---|
| **目的** | 验证审计 H1 的修复：喂狗只发生在控制周期末尾，控制卡死时一定会复位 |
| **注入** | `g_fault_id = 1` |
| **做法** | 让程序继续跑；观察调试器是否掉线（掉线=板子复位了） |
| **观察** | ① 约 200ms 内调试器断开；② 重新连接后 `g_reset_by_iwdg == true`；③ `diag::g_cpu.cycle_count` 归零重新计数 |
| **通过标准** | 200ms 左右复位，且复位原因确实是 IWDG |
| **注意** | 注入点**故意不关中断**——UART/CAN 中断还在跑。这正是"中断还活着但控制死了"的场景 |
| **记录** | 复位耗时 ______ ms；`g_reset_by_iwdg` = ______ |

### T2 · 非法 DBUS 帧（0xFC00 拨轮）→ 不得授权输出

| 项 | 内容 |
|---|---|
| **目的** | 验证审计 H2/F1：校验器与解码器位宽一致，脏数据不会被当成有效指令 |
| **注入** | `g_fault_id = 2` |
| **做法** | 遥控器保持开机；把每帧 DBUS 的拨轮字节改成 0xFC00（低 11 位仍是 1024） |
| **观察** | ① `s_dbus_invalid_frames` 持续增长，`s_dbus_valid_frames` 不再增长；② `lifeState()` 在 100ms 内回到 0（Dead）；③ 车**没有任何动作**；④ 接着看门狗在约 200ms 复位（没有合法帧就不喂狗） |
| **通过标准** | 车不动 + 进入 Dead + 最终复位 |
| **反证** | 把 `kEnableFaultInjection` 关掉、手动构造一帧脏数据，会发现修正前的版本会算出 `rc_wheel≈96`（见 `tests/test_main.cpp` 的对拍用例） |
| **记录** | 进入 Dead 用时 ______ ms；车是否动作：______ |

### T3 · 冻结 IMU 采样 → 演示已知局限（预期**检测不到**）

| 项 | 内容 |
|---|---|
| **目的** | 如实验证审计 F3 的残留风险：读数冻结在"物理上合理的旧值"时，本层的数值检查发现不了 |
| **注入** | `g_fault_id = 3` |
| **做法** | 让云台进入 Working，然后注入 |
| **观察** | ① `GetImu()->isHealthy()` **仍然是 true**；② `yaw()` 不再变化；③ 快速转车体，云台不再补偿（世界稳定失效） |
| **通过标准** | **这一项"通过"的定义就是"复现局限"**：能稳定复现，说明文档记录属实，没有夸大保护能力 |
| **缓解** | 实车上建议在上位机把达妙的 TIMEOUT 设为 50~100ms，并保留硬件急停 |
| **记录** | isHealthy = ______；是否观察到枪口随车体转：______ |

### T4 · 占满 CAN 发送邮箱 → 发送失败必须可计数

| 项 | 内容 |
|---|---|
| **目的** | 验证审计 H4：发送失败不是"静默失败" |
| **注入** | `g_fault_id = 4` |
| **观察** | `s_can_tx_fail_count` 持续增长；控制循环仍在跑（`cycle_count` 继续涨） |
| **通过标准** | 计数能反映失败；关掉注入后计数不再增长 |
| **注意** | 此时电机可能收不到新指令（保持上一帧），务必架空 |
| **记录** | 失败计数增长速率 ______ /s |

### T5 · 1ms 周期最坏耗时（不需要注入）

| 项 | 内容 |
|---|---|
| **目的** | 证明"设计 1ms"真的跑得完 |
| **做法** | 正常上电，遥控器开，让车进 Working；分别静止 / 推满杆 / 小陀螺各跑 30 秒 |
| **观察** | `diag::g_cpu.cycle_ticks_max`、`cycle_ticks_avg`、`overrun_count` |
| **换算** | `cycle_ticks_max / 84` = 微秒 |
| **通过标准** | `overrun_count == 0`，且 `cycle_ticks_max` 明显小于 84000（建议 < 50%） |
| **记录** | max = ______ µs；avg = ______ µs；overrun = ______ |

### T6 · 急停响应（示波器 / 逻辑分析仪）

| 项 | 内容 |
|---|---|
| **目的** | 拿到端到端的急停延迟数字 |
| **做法** | 探头 1：DBUS 信号线（最后一帧拨杆变化）；探头 2：CAN_H/CAN_L 或电机电流 |
| **延迟构成** | 遥控器帧周期（0~10ms，等下一帧）+ 控制周期（≤1ms）+ CAN 发送（约 0.1ms） |
| **通过标准** | 总延迟 ≤ 12ms；软件侧 ≤ 1 个控制周期 |
| **记录** | 实测 ______ ms |

### T7 · 掉线与双板互保（不需要注入）

| 项 | 内容 |
|---|---|
| **做法** | ① 关遥控器 → 观察两板复位；② 拔两板间 CAN 线 → 观察 100ms 内两板都停 |
| **观察** | `lifeState()`、`isOffline()`、电机输出 |
| **通过标准** | 都停，且不出现"一半活着" |
| **记录** | 停机用时 ______ ms |

### T8 · 复位原因核对（配合 T1/T2）

| 项 | 内容 |
|---|---|
| **做法** | 正常上电（按复位键）→ 读 `g_reset_by_iwdg` 应为 `false`；再跑 T1 → 应为 `true` |
| **意义** | 证明 `g_reset_by_iwdg` 确实能区分"看门狗复位"和"手动复位"，T1 的结论才成立 |
| **记录** | 手动复位 = ______；看门狗复位 = ______ |

## 4. 测完的收尾（必做）

1. `fault_injection.hpp` 里 `kEnableFaultInjection` 改回 **`false`**；
2. 重新编译、烧录两板；
3. 调试器里确认 `robot::g_fault_injection_enabled == false`；
4. 跑一遍主机测试：`./tests/run_tests.ps1`（应 171 项全绿）；
5. 提交前搜一下：`grep -r "kEnableFaultInjection = true"` 必须为空。

## 5. 验收时怎么讲（一段话）

> "看门狗不是写在中断里，而是写在控制周期末尾：只有这一轮控制跑完、并且遥控数据
> 是合法且新鲜的，才喂狗。所以我把控制任务注入成死循环以后，中断还在跑，但板子
> 在 200ms 内复位了，复位原因寄存器也确认是 IWDG。非法 DBUS 帧这一项，我把拨轮
> 的高 5 位置脏，校验器直接拒绝整帧，车没有动作、100ms 内回到 Dead。"
