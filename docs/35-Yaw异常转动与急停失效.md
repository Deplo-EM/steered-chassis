# Yaw 异常转动与急停失效

**2026-11-15：整车保持断电，暂停 PID 调试和烧录上车。** 在独立停机保护通过前，任何 PID 候选和本次软件修补都不能据此恢复通电试车。底盘 `kAccLow` 仍待处理，与本次事故分别记录。

**2026-11-16：** 补上了 Yaw 前馈后总力矩越界，以及失能确认过期仍尝试恢复的两个可复现缺口。最新代码、回归和离线 ELF 见 [36 交接复核](36-编号35交接处理与复核.md)。原现场事故的起转和无法停机仍未确认。

## 现场证据

- J-Link 接在云台板上。用户只是观察 Yaw 没有在线改值，左右推右摇杆后两次出现 Yaw 自行匀速转动；拨右下急停仍在主动转动，只能关电源停止。
- 未确认出事时 Ozone 是否暂停 CPU，也未确认实车两块板的实际 ELF。`gimbal_dsh_B07.jdebug.user` 保留了 Yaw 采样配置，不能证明当时烧录的就是 B07，也没有提供停机当拍的采样数据。B08 等 PID 候选保留原样，只作对照。
- 尚不清楚最初为什么自行转、急停指令到没到云台板、CAN 帧有没有到电机，不能把报告的两次都归因于增益、断点或驱动端的一种故障。

## 已确定的固件缺口与修补

旧版急停把 `Gimbal::stop()` 的两轴力矩请求写零，但通信任务仍然让普通编码器生成电机指令。电机如果回报未使能，自动使能逻辑甚至可能再发使能指令。此前测试只看了控制量归零和发帧次数，漏掉了帧内容与驱动反馈。

现版云台在上电无授权、急停和撤权时，撤销旧控制帧，只向两轴发送明确失能指令。两路 CAN 各自撤销旧邮箱；一路未完成时，另一路的失能帧不会被反复取消。只有收到有效急停确认、两轴报告正常失能、操作者后来解除急停且对板授权有效，才允许新的使能请求。未获得两轴使能反馈前，力矩维持零；使能握手超时或运行中意外丢失使能，需要重新确认急停。

修改和验证入口：[云台授权状态机](../Gimbal/RobotModules/component/robot.cpp)、[CAN 发帧](../Gimbal/Task/component/comm_task.cpp)、[主机集成回归](../tests/test_robot_safety.cpp)。PID 参数、底盘固件、接线和电机内部设置不属于本次修补。

验证构建：`Gimbal/build/estop-latch-verification/steered_gimbal.elf`，SHA-256 `5C0C2A5905399538BDEDD33DE4342B714F858110DC0F6E752BC37E7605F27F82`。它用于核对固件，未进行实车下载；基于构建时的工作树，不能拿旧 Ozone 工程当作这个 ELF 的符号文件。`SAFE-BUILD` 只表示故障注入关闭。已核验底盘 `imu-sample-fix`、云台 B07 和 B08 原 ELF 的散列未变。

主机回归用真实云台状态机和发帧代码、模拟 CAN 和驱动应答。首次复现中旧代码未通过 9 项检查，含上电不失能、急停帧内容不对及非预期再使能。修补后云台安全组 81 项、全套 1,895 项检查全部通过，覆盖本地急停早于对板、未收到失能反馈禁止恢复、握手超时、运行中掉使能、两路分别撤销旧帧。此结果不能替代实际驱动器和物理停机验证。

## 下一步怎样区分原因

如果 Ozone 仍显示事故前后已经采到的 Timeline 或 Console，保留它和项目名；无需重新上电或连接。单看 J-Link 已连接，不能证明核心在当时是运行还是暂停。

| 能拿到的证据 | 指向哪一段 |
|---|---|
| 采样中 `uwTick` 停住或 Ozone 明确显示 Halt / 断点 | 软件可能没继续读遥控或没执行停机任务；不能靠同一 CPU 发帧来兜底。[SEGGER 对暂停调试的说明](https://kb.segger.com/Monitor_Mode_Debugging) |
| 核心继续运行、`estop` 未变成 1 | 优先核对有效 DBUS 右档、云台急停输入和状态更新；不要先动 PID。 |
| `estop=1`、`authorized=0`，或软件停止发旧力矩，但电机仍出力 | 区分失能发送请求、CAN 完成和驱动器实际失能，三者不是同一个证据。用动力隔离后的台架和总线记录核对，无需在整车上重现。 |
| Yaw 目标或反馈在最初自行转动之前已经异常 | 可用已保存的目标、反馈、力矩请求和故障时刻定位起转；这与“为什么不能停”分开查。 |

## 恢复通电调试的条件

1. 先在**执行器动力隔离**的台架核对新版发帧，以及急停沿不会继续发旧控制或使能指令。软件测试模拟的反馈不能当作真电机证明。
2. 核实一种独立于两块控制板和 CAN 的断动力手段，操作者从运动范围外就能使用。再由具备条件的台架核实实际驱动端是否启用了 **CAN 通信超时保护**，以及静默后确实停止主动输出。厂商提供这项设置，不代表这台车当前已经启用；按组里要求只读核对原配置，不私改电机参数。[达妙驱动控制协议 V1.4（第 10 页与第 37 页）](https://github.com/dmBots/damiao-document/blob/master/%E8%B0%83%E8%AF%95%E5%8A%A9%E6%89%8B%E4%BD%BF%E7%94%A8%E8%AF%B4%E6%98%8E%E4%B9%A6%EF%BC%88%E8%BE%BE%E5%A6%99%E9%A9%B1%E5%8A%A8%E6%8E%A7%E5%88%B6%E5%8D%8F%E8%AE%AE%EF%BC%89V1.4.pdf)
3. 整车不做动力通着时的暂停、断点或故障重现。控制板卡死、复位尚未完成或 CAN 无法发送时，软件失能帧可能发不出去。只有上述保护确实生效，并在受控工况确认两轴停止主动出力后，才讨论恢复空载云台调参。失能撤掉力矩，机构仍可能惯性滑行或被重力拉动，台架要约束其运动范围。
