# 底盘与云台撤力路径审计（R3）

2026-11-17。沿遥控接收、双板授权、状态机、闭环、CAN 提交和驱动器输出逐层核对。裁决依据为本地《Hello World 电控组步兵（舵轮）考核说明（已补全）》第 3、7–9、11 页：未进入 Working 或遥控急停／失联时归零，板间真正失联进入保护，保留看门狗、舵角变化率和轮速限幅、Pitch 软件限位。此轮未变更接线、轮位、PID 系数、电机设置或刮擦区。

## 已收窄的三处

| 原触发 | R3 行为 | 仍会停的情况 |
|---|---|---|
| 底盘本板 IMU 判废，分离或小陀螺也退出 Working；云台还重复检查底盘 IMU 状态位 | 底盘完成标定、自检并进入 Working 后，分离／小陀螺以仍新鲜的 Yaw 关节角工作；底盘 IMU 状态保留作诊断。云台依赖自己的 IMU 和底盘明确的使能授权 | 首次上电和故障恢复仍要 IMU 自检；跟随档需要底盘陀螺做阻尼，自身 IMU 不可用时停止。云台本板 IMU 故障仍撤力 |
| 实测已经到位，逆解的旧限速参考还在远处，四个轮速继续等；舵环还可能沿旧目标用错方向出力 | 新目标已进入现有的 0.08 rad 全驱动误差范围时，就地舍弃过期的舵角参考并清该轮 PID 历史；仍按最大舵角变化率向新目标移动 | 实测舵角跟不上、舵持续顶住或没有可达路径，原判定仍生效 |
| 一帧例行双板状态碰到邮箱暂满，就与发送失败一起触发两板撤力 | 例行状态在下一控制周期重试；同周期的真实遥控分片优先于例行状态。统计仍记录被延后的发送 | 急停、授权变化、底盘要求 Yaw 停止或反向时，关键帧不能延后。硬件 bus-off、已排入帧未确认或超时、实际电机帧和遥控分片提交失败仍进入原保护 |

CAN 的“已排入邮箱”与“硬件确认已发送”在代码中仍分开处理，见 [STM32F407 RM0090 的 bxCAN TXRQ、RQCP、TXOK 和 ABRQ](https://www.st.com/resource/en/reference_manual/dm00031020-stm32f405-415-stm32f407-417-stm32f427-437-and-stm32f429-439-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf)。最终是否卸力仍只能由实车验证。

## 所有撤力入口

| 触发源 | 底盘 | 云台 | 现场辨认 |
|---|---|---|---|
| 急停：有效右拨杆下档，或收到可信的对板急停 | 四驱、四舵归零；必要时撤销仍在邮箱里的旧帧 | 两轴力矩归零，发送达妙失能帧并撤销待发旧帧 | 看当前 `estop_`；正常拨下可仍显示 Working |
| 无有效遥控、新鲜度到期、改换遥控来源未重新确认 | 不接受旧输入；进入／保持 Dead，清运动目标。合法单帧有自己的新鲜度，非法帧不能续期 | 底盘遥控在线／授权位消失后停止；本地右拨杆急停仍直接有效 | 底盘 `last_dead_.causes` 含 4（遥控）或 64（未授权） |
| 对板失联、未就绪、重启或撤销许可 | 丢失云台的新鲜关节角或 Working 状态停止 | 对板通信真正超时进 Dead；对板发“不许可”时双轴已失能，云台状态仍可能是 Working | 底盘原因位 32，配合 `peer_online_`；云台看 `g_gimbal_dbg.authorized` |
| 未初始化、启动自检、复位后的授权 | 未进 Working 各电机归零；进入前须自检，且收到有效急停确认 | 未进 Working 保持失能；只有可信急停确认、双轴最新失能反馈和明确授权齐备才请求使能；在两轴反馈确认使能前不输出力矩 | `state_`、`authorized` 与实际力矩分别观察 |
| 用于闭环的 IMU 不可用 | 跟随档和自检／恢复时停；已运行的分离／小陀螺见上表 | 自己的 IMU 不可用时双轴停；兼容已授权时原有的 8 ms 特定低模长保留，本拍用旧姿态时不积分新的 Yaw 目标 | 底盘原因位 8；云台 `last_dead_reason` 位值 2；看停机快照而非事后恢复的实时值 |
| 电机反馈离线、不健康、数值不可信 | 驱动或舵电机任一反馈离线／异常，整组停止；舵角越界保留轮位 | 两轴任一反馈离线、非有限值、驱动器报故障、运行中意外失能或使能确认超时，双轴停 | 底盘原因位 16；云台原因位 4／8／16 |
| 速度为零、轮组没有滚动需求 | 相应驱动电流归零，舵角仍可保持；分离档松杆会先减速 | Yaw 摇杆回中停止积累新目标，仍闭环保持 | 输出为零不代表退出 Working；看指令和实测 |
| 舵角对齐等待、换向 | 确有需求的轮存在对齐误差，先不给驱动轮电流，舵电机仍纠偏。普通构建等待 300 ms 只记超时；不单独置 Dead | 不是独立的云台停机条件 | `g_chassis_dbg.align_blocked_mask`、`drive_ready`；比较 `steer_feedback`、`steer_desired` 和 `steer_target` |
| 舵电机持续较大输出却无有效位置进展 | 锁存真实堵转判定并整组撤力；不能靠持续顶着刮擦恢复 | 底盘随状态撤销云台许可 | 底盘原因位 1；`last_steer_stall_`、`g_steer_stall_tx` |
| 已配置的避让区内确实无可达舵角；或起点落在禁入区 | 四驱四舵归零、撤销未发旧帧；状态可能仍是 Working。只有之后的反馈和输入重新得到有效路径才出力 | 不单独撤销云台许可 | `steer_keepout_blocked_mask` 非零；`steer_keepout_configured_mask` 当前为 0，因此现有实车不能把普通不动归因于绕行配置 |
| 非法目标、求解失败、闭环或编码拒绝 | 清本拍非法目标／电机输入；控制帧编码失败上报 CAN 保护 | 非有限目标或角速度、控制器实际拒绝输出时整组归零；驱动器报错仍不能放行 | 区分底盘局部输出归零和 Dead；云台 `last_dead_reason` 位值 64 表示闭环执行失败 |
| Pitch 接近或处于行程边界 | 下发目标做角度钳位 | 在边界只禁向外力矩；向内退出仍可控，Yaw 继续，不进 Dead | `pitch_at_limit` 属于限位提示；它自身不撤销云台许可 |
| 真的 CAN 发送故障、旧帧未撤掉 | 撤销授权、尝试发零；关键提交失败、完成超时或 bus-off 不降级成例行重试 | 同一监督规则，发送失能而非普通 MIT 力矩 0 | 底盘原因位 2，云台 32。连续失败约 10 ms 后停喂狗；故障恢复前需有效急停确认和成功发送窗口 |
| 控制任务没运行到末尾或有效遥控持续离线 | 不喂狗，随后 IWDG 复位 | 同样受看门狗约束 | 明确区分 `uwTick` 持续增长时的 Dead 与复位后从零开始 |

原因位可以叠加。例行状态被延后也会增加发送失败统计，**仅看总计数不能判定停机原因**。故障先看底盘 `s_robot.last_dead_` 或云台 `robot::diag::g_gimbal_dbg.last_dead_reason` 和 `last_dead_tick_ms`。若 Working 下不动，再看授权、对齐和避让掩码。

首跑锁定、单舵探针和历史排除轮只属于各自的构建配置。首跑还会受专用中位确认、降速停车、对齐超时规则影响；探针不开放常规三模式；云台首跑锁定只发失能帧。这些限制未进入 R3 考核构建。

### 两个轮子刮擦

两支都不通时停是故障兜底。正常驾驶频繁走到该分支，依然不能算通过。当前两个轮的实测刮擦区角度尚未录入；R3 不能绕开未知的碰撞。应按 [43 号记录](43-两轮刮擦绕行与限速简化.md) 确定每轮可转范围，保证舵轮有机械间隙或确实存在可用等效路径。在硬刮擦仍发生时，让其他轮拖着走会增加横向拉扯，也不能保证平移方向。
