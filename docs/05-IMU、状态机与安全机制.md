# 05 · IMU、状态机与安全机制

> 这篇讲两件事：姿态是怎么算出来的；以及**这台车在什么情况下会停下来**。

---

## 1. IMU 的数据流

```
   BMI088 芯片（SPI1）
        │  加速度 ax,ay,az（m/s²，含重力）
        │  角速度 gx,gy,gz（rad/s，含零漂）
        ▼
   ┌──────────────────────────────┐
   │ Imu::update()                │
   │  ① getData() 读芯片           │
   │  ② 标定阶段：累计角速度均值    │
   │  ③ 扣零漂  g -= bias          │
   │  ④ Mahony::update(acc, g)     │
   │  ⑤ getEulerAngle() → r/p/y    │
   └──────────────┬───────────────┘
                  │ roll / pitch / yaw（rad，相对"标定完成那一刻"）
                  ▼
      底盘板：跟随时用 gyroZ() 做阻尼
      云台板：yaw 用在世界角闭环里（核心）
```

### 1.1 为什么一定要做零漂标定

陀螺仪静止时输出不是精确的 0，而是有个几十 mrad/s 的偏置。这个偏置会被 Mahony **积分**：

```
漂移角 ≈ 偏置 × 时间
0.02 rad/s × 10s = 0.2 rad ≈ 11°
```

10 秒就漂了 11°，云台 yaw 会慢慢自己转走。所以必须：

1. 开机静止采样 2 秒（2000 个点，1kHz）；
2. 求平均得到 `bias`；
3. 之后每帧减掉它。

### 1.2 标定期间的三个保护

| 保护 | 做法 | 为什么 |
|---|---|---|
| 不许输出 | 标定未完成时 `yaw()` 等返回 0，状态机停在 Dead | 拿带偏置的角度去控制 = 车自己慢慢跑 |
| 运动自动重来 | 采样值与当前均值差 > 0.5 rad/s → 清零重来 | 上电时有人碰车，会把运动当成偏置 |
| 标定完成后重新初始化 Mahony | `ahrs.init()` | 让"零点"精确定义在标定完成那一刻 |

### 1.3 姿态角的含义与局限

- **相对**：roll/pitch/yaw 都是"相对标定完成那一刻的姿态"，不是绝对地理方向；
- **会慢漂**：Mahony 的 yaw 没有磁力计校正，几分钟会有几度的漂移；
- **够用**：跟随模式只关心"车头相对云台的夹角"（毫秒级），不关心绝对方向。

> 这也是为什么 δ 用的是**电机关节角**而不是两个 IMU 的差值：
> 关节角没有漂移，精度也更高。IMU 的 yaw 只用来做云台的世界稳定。

---

> 当前实现补充：IMU 候选样本先校验再发布，坏样本保持上次有效值但 `isSampleValid()` 当次为 false。
> `isHealthy()` 为50坏/100好的长期迟滞；控制资格同时要求标定、健康和当次有效。
> 底盘上电、遥控掉线及任何安全故障退回 Dead 后都需再次收到有效急停档确认，才能恢复。
> CAN 首次关键帧失败锁存并清零，连续失败10ms停喂狗；有效急停且连续100ms成功提交才解除锁存。
> 详见 `docs/06`、`docs/11`，硬件实际卸力仍须实测。

## 2. 状态机

### 2.1 三个状态

```
   ┌─────────┐  条件全满足   ┌──────────────┐   500ms   ┌─────────┐
   │  Dead   │ ────────────▶ │ Resurrection │ ────────▶ │ Working │
   │ 输出全 0 │ ◀──────────── │  输出全 0     │ ◀──────── │ 正常控制 │
   └─────────┘   条件丢失     └──────────────┘  条件丢失  └─────────┘
```

| 状态 | 输出 | 做什么 |
|---|---|---|
| Dead | 全部 `setInput(0)` | 等待条件；IMU 在后台标定 |
| Resurrection | 全部 `setInput(0)` | 等 500ms 让状态稳定（**不做任何动作**） |
| Working | 正常控制 | 按模式生成指令 |

> Resurrection 里"舵角回中"这个动作已经**删掉**了（审计 H3）：考核红线写的是
> "生命状态未进入 Working 时，所有电机必须立刻输出归零"。回中虽然好看，但它是一次
> 无人下达的运动指令，按红线判会不通过。宁可少一个花活，也不能踩线。

### 2.2 进入 Working 的条件

| 条件 | 底盘板 | 云台板 |
|---|---|---|
| 遥控器在线（本板 DBUS，合法帧） | ✅ **必须** | — |
| 对方板在线 | ✅ 且对方已 Working | ✅ 只看帧在不在来 |
| IMU 标定完成 **且数据健康** | ✅ | ✅ |
| 电机全部有反馈 | ✅ 8 个 | ✅ 2 个 |

> ⚠️ **接收机接线**：底盘板**必须**自己的 USART3 接 DBUS 信号，否则进不了 Working。
> 云台帧里的 `dbus_online` 只用于**喂狗保活**，不提供摇杆数据，不能让底盘动起来。
> 如果实车只能把接收机接在云台板，需要扩展协议（把摇杆值也传给底盘），属于另一个方案。

**只要有一项丢失，立刻回 Dead 并归零**，不做"再等等看"。

### 2.3 为什么底盘板要求云台先 Working

枪口在乱晃（云台还没稳住）的时候开车，操作手根本不知道"前"在哪。
所以底盘板的准入条件里包含 `gimbal_data().working`。

**为什么不会死锁**：云台板的 Working 条件里**没有**"底盘板 Working"，只有"底盘帧在来"。
两板都从开机就在发帧，所以云台先到 Working，底盘随后跟上。

## 3. 五层安全保护

从外到内，任何一层触发都会让车停下：

```
第 5 层  看门狗（200ms 没喂 → 整机复位）
   ▲
第 4 层  双板互保（对方掉线 → 停止出力 / 整机复位）
   ▲
第 3 层  面板状态（急停档 / 遥控器离线 → 输出归零）
   ▲
第 2 层  状态机（Dead/Resurrection → 输出归零）
   ▲
第 1 层  控制律自身（速度/加速度/电流/电压/力矩限幅）
```

### 第 1 层：限幅

- 平移 ≤ 2 m/s，自旋 ≤ 6 rad/s，加速度 ≤ 8 m/s²
- 舵角变化率 ≤ 10 rad/s，轮速 ≤ 3 m/s
- 轮电流 ≤ 8 A，舵电压 ≤ 20000，云台力矩 ≤ 3.5 N·m
- PID 输出、积分均有独立限幅

### 第 2 层：状态机

非 Working 时 `chassis->stop()` / `gimbal->stop()`，把 8+2 个电机全部 `setInput(0)`。

### 第 3 层：急停与离线

- 右拨杆打到最下 = 急停 → **在 `applyOutput` 的最外层判断**，任何模式都绕不过；
- 遥控器 100ms 无数据 → `isRemoteOnline()` 为假 → 状态机回 Dead。

### 第 4 层：双板互保

- 云台板 100ms 收不到 C2G → 停止出力；
- 底盘板 100ms 收不到 G2C → 回 Dead；
- 更狠的是看门狗（下一层）：一方的遥控器没了，两方都会复位。

### 第 5 层：看门狗

**每块板只有一个喂狗点**：`CommTask` 的最后一行。而 `CommTask` 是由 TIM6 中断在
`MainTask()`（控制、逆解、闭环、下发）**之后**调用的。

| 板 | 喂狗位置 | 喂狗条件 |
|---|---|---|
| 底盘 | `Chassis/Task/component/comm_task.cpp`（唯一） | 本板 100ms 内收到过**合法** DBUS 帧，或云台帧说它那边遥控器在线 |
| 云台 | `Gimbal/Task/component/comm_task.cpp`（唯一） | 本板 100ms 内收到过**合法** DBUS 帧，或底盘帧说它那边遥控器在线 |

> **为什么不放在中断里**（这是审计 H1 抓到的真问题）：
> UART/CAN 中断的优先级都高于 TIM6。如果把喂狗放在中断里，那么哪怕控制循环
> 因为 SPI 卡死、死循环而完全停住，中断照样会进来喂狗——看门狗永远不会复位，
> "任务卡死 200ms 复位"这条验收项就是假的。
> 现在中断只记录"收到了一帧合法数据"的时间戳，喂狗统一在控制周期末尾。

**效果**：
- 关掉遥控器 → 没有新的合法帧 → 不喂狗 → 200ms 后复位；
- 控制循环卡死 → 走不到 CommTask → 不喂狗 → 200ms 后复位；
- 串口被噪声/错位喂了 18 字节垃圾 → 校验不通过 → 同样不喂狗。

> 达妙电机有个特性：**不发指令就保持上一帧的动作**。所以"停"必须靠持续发 0 力矩，
> 或者靠复位让它失能。这正是看门狗在这里的价值。

## 4. 什么情况会让车停下（故障树）

| 触发 | 车会怎样 | 怎么恢复 |
|---|---|---|
| 右拨杆打到最下（急停） | 立刻停，状态保持 Working | 摇杆回中并确认允许恢复后解除急停 |
| 遥控器关机 / 没电 | 约100ms在线阈值后软件清零；复位还需叠加IWDG超时，实测为准 | 开遥控、保持有效急停确认，全部条件就绪后再解除 |
| 两块板之间 CAN 线拔掉 | 0.1s 内两板都停 | 插回，等自检 |
| 某个电机信号线断 | 状态机回 Dead（要求全部电机在线） | 修线，复位 |
| IMU 初始化失败（片选接反） | 永远停在 Dead，车不动 | 对调 CS 引脚 |
| 遥控器没开机就上电 | 板子 200ms 复位一次，反复重启 | 先开遥控器 |
| 代码跑飞 / 死循环 | 200ms 后整机复位 | 正常，这就是看门狗的作用 |

## 5. 调试时怎么看"现在为什么不动"

在调试器里看这几个变量（都在 `GetRobot()` 里）：

| 变量 | 含义 | 期望 |
|---|---|---|
| `lifeState()` | 0 Dead / 1 Resurrection / 2 Working | 2 |
| `isRemoteOnline()` | 遥控器是否在线 | true |
| `isEstopped()` | 急停是否生效 | false |
| `areAllMotorsOnline()` | 电机是否全在线 | true |
| `GetImu()->isCalibrated()` | 零漂是否标定完 | true |
| `GetImu()->errorState()` | IMU 芯片错误码 | 0 |
| `GetGimbalChassisComm()->isOffline()` | 对方板是否离线 | false |

按顺序查一遍，基本 30 秒就能定位"卡在哪一层"。

CAN 持续失败时即使有新鲜 DBUS 也不喂狗；任何 Dead 迁移都会撤销底盘旧授权，包含云台单独复位。
