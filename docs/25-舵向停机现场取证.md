# 舵向停机现场取证

现场现象：左上分离档推左杆，或从左上切到左中跟随后，底盘进入 Dead。云台仍为 Working 但撤销出力。两板 `uwTick` 未见重启，底盘 `alignment_at_stall_` 曾为 15。右下急停确认后恢复 Working，仍不能证明舵轮能执行控制。

本轮没有改变 CAN 路由、舵电机模式、PID 或停机阈值。新增的是普通底盘固件的停机记录，不是单电机探针，也不需要改云台固件。本机保留旧的 `Chassis/build/steered_chassis.elf` 用于观察当前板上固件。

1. 如由现场队员安排继续验证，先固定车架并架空四轮，隔离电机动力，保持右下急停，按常规流程仅给底盘烧 [停机记录 Ozone 工程](../debug/ozone/chassis_stall_trace.jdebug) 对应的 ELF。不要把新 ELF 用 Attach 配到仍烧着旧版的板。新工程路径指向 `Chassis/build/stall-trace/steered_chassis.elf`，正常控制与原版一致。
2. 确认急停有效、两板就绪后，在左上分离档只做一次短测。若复现，回右下急停，不需要再试，也先不要复位。读取两份记录，`sequence` 应相同且大于 0；当前锁存 `steer_stall_mask_` 清零不影响这两份记录。

| Ozone 位置 | 字段 | 含义 |
|---|---|---|
| `s_chassis → last_steer_stall_` | `stall_mask`、`alignment_mask` | 前者是触发保护的轮组，后者是当时所有未对齐轮组。位 0～3 依次左前、左后、右后、右前。 |
| 同上 | `measured_rad`、`target_rad`、`requested_raw`、`feedback_amp` | 停机前同一控制周期的实际角、限速目标角、PID 电压请求和反馈电流；按物理轮组索引。 |
| `robot::diag::g_steer_stall_tx` | `has_recent_txok`、`frame_id`、`command_raw` | 停机附近是否观察到一条非零舵向帧的硬件 TXOK、该帧 ID 和四个有符号设备槽位值。发出不等于指定电机执行。 |
| 同上 | `tick_ms`、`attempted_nonzero`、`queued_nonzero`、`confirmed_nonzero`、`unconfirmed_nonzero` | 停机时刻与上电以来的累计发送依据。后 3 项仅统计带回执的非零帧，不能与尝试数简单相减求丢包。 |

判别顺序：

- `sequence=0`：没有捕获舵向停滞。这次若仍进 Dead，转查 CAN 故障锁存、电机在线、板间与 IMU。
- 有停机记录但 `has_recent_txok=false`：没有近期非零帧完成证据。若要定位发送，从 CAN1 的只读抓包或完成状态着手；没有证据不等同于没发。
- 有 `0x1FF` TXOK，对应槽位非零：再比较触发轮的实测角和电流。如无电流响应，优先对照同车正常固件在 CAN1 的实际帧、设备槽位和配置；若有电流但角度无进展，优先核对机械、反馈新鲜度和方向。单个电流快照不能代替趋势，送达与执行仍需要现场结果。

如果不方便重烧，保留原版，用只读 CAN 抓包对照非零 `0x1FF` 和触发轮对应的 `0x205`～`0x208` 反馈即可。

离线验证：主机 1510 项、0 失败，含切跟随触发停滞和急停确认后记录保留；独立底盘 ELF 构建通过，SHA-256 为 `C8F8847136A131FB1B52132F70861663B540B29A5F311572E65CF6B8281CED8A`。旧底盘和云台 ELF 哈希与 docs/22 一致。尚未烧录或上车验证。

## 现场回报：已捕获第 1 次和第 3 次停机

两份记录的序号各自一致。底盘 CAN1 均有近期非零 `0x1FF`（十进制 511）TXOK；这排除了“该时刻一条非零舵向帧也没发出”，不证明指定舵机执行。

| 现场操作 | 序号和底盘时钟 | 触发掩码 | 对齐阻塞掩码 | 带回执帧累计 |
|---|---|---|---|---|
| 分离档推左杆后 | 1 / 42739 ms | 15，四个软件轮位 | 0 | 入邮箱和确认均为 3207，未确认 0 |
| 急停确认后切跟随 | 3 / 110544 ms | 5，代码的左前和右后 | 15，四个软件轮位 | 入邮箱和确认均为 4378，未确认 0 |

对齐掩码只计入有非零轮速目标的轮组；舵向停滞检查还会看保持舵角时的输出。因此第 1 次的 0 不等于四个实际角已经到位。第 3 次的四个数组内容在截图中未展开，仍需读 `command_raw`、`feedback_amp`、`measured_rad` 和 `target_rad`。右下急停后直接读已有记录，无需再推杆或重烧。现场未证明实车问题已修复。

## 第 7 次：大幅非零电压命令已确认发送，停机时反馈电流接近零

两份快照均为序号 7，底盘时钟 246094 ms，`stall_mask=5`、`alignment_mask=15`。CAN1 最近的非零 `0x1FF` 已得 TXOK；当时累计 29783 条入邮箱并确认的非零帧，未确认累计为 0。

帧为 `0x1FF / 8 字节 / 36 2F DE E4 25 E7 E4 37`。报文和 PID 符号相反符合四只 GM6020 的反向配置；最近完成帧与停机计算不是同一控制周期。四路单个电流快照均小于 0.02 A，优先查驱动器是否接受命令、是否被其他发送者覆盖；它不能单独排除间歇出力或证明电流模式已开启。

优先在保持急停时观察 GM6020 灯态；若队员可协助，读取 RoboMaster Assistant 电流环和驱动状态（不写入），或在同一台车上用正常固件只读抓取 CAN1 的实际帧。大疆 GM6020 v1.4 手册注明：橙色常亮表示电流模式收到电压指令。若两版都用 `0x1FF`，再比较是否有另一发送者的同 ID 零帧、驱动器状态及 `0x205`～`0x208` 反馈随命令的变化。禁止用加大输出或放宽门槛来判断。

## 现场报告橙灯常亮：独立底盘电流候选版

现场人员确认照片中的橙灯常亮。若该灯是 GM6020 本体指示灯，这说明至少该舵机在电流模式下收到了电压指令；不能据此推断四只全都切换过。结合第 7 次的 `0x1FF` TXOK 和接近零的反馈电流，先在底盘固件一侧验证协议匹配，不修改电机设置，也无需 RoboMaster Assistant。旧电压固件下不必重复推杆取证。

- Ozone 工程：[chassis_steer_current_field.jdebug](../debug/ozone/chassis_steer_current_field.jdebug)。对应 `Chassis/build/steer-current-field/steered_chassis_steer_current_field.elf`，构建开关 `ROBOT_STEER_CURRENT_FIELD=ON`。普通构建仍是电压版；此选项和单舵诊断探针互斥。云台和原先两份底盘 ELF 保留。
- 候选版在底盘 CAN1 使用 `0x1FE`。舵角 PID 仍用原有数值标度，其输出上限对应 ±1.2 A 初测限幅；这是本次初值，不能由电压满量程换算得出。`last_steer_stall_.requested_raw` 仍是 PID 标度，`g_steer_stall_tx.command_raw` 才是实际电流报文槽位的值。驱动轮、急停、看门狗、对齐门和舵向停滞条件沿用停机记录版。
- 未做实车验证。有固定架空条件时，只烧底盘，保持右拨杆下档，先确认启动和急停。首次有动力验证用左上分离档，短时观察四轮舵角是否向目标收敛；随后按急停确认输出归零。有轮组不跟随、反转、抖动或再次进 `Dead`，回急停后读停机记录，不重复推杆、不加电流。未逐轮确认模式和响应前不落地试车，不先试跟随或小陀螺。
