# 下次实车调试应对表

适用：`docs/22` 所记录的正常底盘和云台固件，首次配套上车。当前只有离线构建和主机测试证据。这里列的是预测和判别方法，不是已确认的实车故障。只针对底盘、遥控和两轴云台。

## 出发前和现场的头几分钟

1. 带上 [底盘](../debug/ozone/chassis.jdebug)、[云台](../debug/ozone/gimbal.jdebug) 两份 Ozone 工程及各自 ELF；另带 [ID 2 台架探针](../debug/ozone/chassis_steer_probe.jdebug)，不要把它当正常固件。以 [`docs/22` 的哈希](22-舵轮回归修复与台架核对.md#5-本轮离线证据) 核对文件，现场记下烧录成功的两块板和文件名。带原 J-Link、能录屏的电脑；能借到的话，让队员带只读 CAN 记录设备。
2. 车架固定、四轮离地，有人能直接切断驱动电源。**烧录时隔离电机动力，目标板逻辑供电按现场规程接好。** 各板 `Program & Verify` 后 `Reset & Run`。继续观察本板无需 Stop；换板时先急停、结束会话、按规程断电再换。只是查看运行状态时选 `Attach to Running Program`，别让默认的下载模式再烧一次。Ozone 左下 Running 表示 CPU 在跑；`kWorking` 才表示应用已过准入。驱动动力隔离时缺电机反馈而停在 `Dead`，不能据此判断故障。
3. 正式试车前，遥控器先开，**左上分离、右下急停、两杆和拨轮回中**；两板和驱动按规程一起上电，车与云台静止，等两板标定。底盘开 `s_robot`、`s_chassis`，云台开 `s_dbus_valid_frames`；对少量关键项启用实时刷新。无探针、右下显示 `Disconnected` 或 Refresh 为 Off 时，不能把空白或缓存当实测零值。
4. 两板能稳定 `kWorking`、右下急停仍生效后，才进入第一次动作检查。只试左上分离：解除急停先观察回中是否有主动驱动，再推一点左杆、回中、急停。**先看轮组朝向，再看轮胎滚动。** 要落地、试自旋或做失联注入，按队里的台架顺序，别把首次上车变成三模式同时试。

## 一上电就不动：从云台接收机向后查

| 看到什么 | 先看哪里 | 当场怎么处理 |
|---|---|---|
| Watch 没数值，或推杆完全无响应 | Ozone 是否 `Connected` 与 `Running`；加载的是否是该板、该版本 ELF；Refresh 是否开启 | 保持急停，确认连接和符号。若连接时 CPU 已暂停，隔离动力，恢复运行后再按上电流程；不要带动力用断点找实时量。 |
| `uwTick` 或 `g_cpu.cycle_count` 增长后反复归零 | `g_reset_by_iwdg`、云台合法 DBUS 是否增长、两板 CAN 发送故障 | `g_reset_by_iwdg=1` 只说明最近一次复位的原因。反复归零才是循环复位证据；按 DBUS → 板间 → CAN 发送顺序找为何没有持续喂狗。只烧单板时复位循环不能用来定整车故障。 |
| 云台 `s_dbus_valid_frames` 不增长 | 同看 `s_dbus_invalid_frames`、`s_dbus_partial_frames` | 无回调和有帧却不合法分开查：前者核对遥控器与云台 USART3 接收链路；后者记录帧长度、拨杆和值域，先别放宽校验。底盘本地 DBUS 为 0 在云台接收方案中正常。 |
| 云台有效帧在涨，底盘遥控仍离线 | 底盘 `peer_online_`、`peer_input_.dbus_online`；转发 `0x212`～`0x214`，不是只看一个在线位 | `peer_online_=0` 先查板间状态 `0x210/0x211`、是否混烧；对板在线但 `remote_input_.online=0`，核对转发是否完整，并保持右下急停给底盘选源。来源选上后应为 `kGimbal`。若需分析，可读 `s_robot.comm_` 内的接收计数；不要为了绕开转发临时改 CAN 路由。 |
| 一直 `Dead`，或 `Dead` 与 `Resurrection` 来回跳 | 底盘 `remote_armed_`、`peer_input_.working`、`motors_online_`、`can_tx_guard_.faulted_`；云台看自己的 `state_`、`motors_online_`、`s_imu` | 右下急停确认后查第一个不满足的条件。底盘依赖云台先 Working，云台进 Working 只要求底盘状态帧在线等自身条件，不需要底盘先 Working。进入恢复自检后需连续约 500 ms 条件正常。 |
| `motors_online_=0` | `motor_checkers_` 中哪个时间戳不更新；底盘 0～3 是驱动，4～7 是转向。CAN1 期望 GM6020 `0x205`～`0x208`；CAN2 期望 M3508 `0x201`～`0x204`；云台 Yaw/Pitch 期望 `0x11/0x12` | 根据缺的轮位或轴核对 ID、反馈与实际供电。`rx_header1/2` 只是最近一帧，看到某 ID 是正证据，没看到不能断言不在线。队友固件能跑时，优先同车同线做只读对照。 |
| `s_imu.calibrated_=0`，或运行后忽然掉资格 | `samples_` 有无增长或归零；`rej_transport_`、`rej_fresh_`、`stale_gyro_` 哪个涨，两块板分开判断 | 车静止重新观察；样本不增长查采样链路，有累计但反复归零查运动/振动和重标定触发。同录 `g_cpu.overrun_count`，持续增长再查任务时序。不要靠延长旧样本有效期起车。 |
| `can_tx_guard_.faulted_=1` 或刚动就掉回 `Dead` | `failed_cycles_` 和 `s_can_tx_fail_count` 是否在涨；CAN 控制器是否 bus-off；哪块板先报 | 在急停下找发送失败方向。提交计数为 0 仍可能有 TX 完成失败。先恢复正常通信，再保持新鲜右下急停，CAN 保护需连续约 100 ms 正常才清锁存，并重新走自检；持续掉线时不要反复推杆。 |
| 空载能工作，一给力就整板重启 | 是 `state_` 变了还是 `uwTick` 归零；最近一次 `g_reset_by_iwdg`、另一板是否同时掉线 | `uwTick` 归零但没有看门狗标志，不能按软件保护解释；先停，请队员测起动时电源是否掉压，并检查重启只发生在哪块板。若看门狗标志为 1，先留存 CAN 或控制耗时的证据。 |

## 到了 Working，推杆后仍没反应

在分离模式，拨轮回中。画面必须配合轮组实际动作；看 RAM 缓冲区只知道软件算出了什么。

| 证据 | 下一步 |
|---|---|
| `estop_=1`，或 `remote_input_.lv` 不变 | 看两端原始 `right` 是否下档 `2`／中档 `3`，云台的急停回传是否还在；先在急停下确认摇杆通道变化。归一化约 2% 死区，轮组另有 0.02 m/s 的零速阈值；极轻的杆量可能正常无动作。 |
| `lv`、`ramped_.vx` 已非零，但轮子不滚 | 看 `s_solver.command_[i]` 的 `speed/desired_angle`、`s_chassis.align_blocked_mask_` 及 `drive_ready_`。计时到 300 ms 只报超时，不打开驱动。掩码 bit 0～3 分别为左前、左后、右后、右前。 |
| `s_steer_frame` 非零，四个实际舵角不变，`s_wheel_frame` 为零 | **这最像上次。** 对齐条件解释了轮胎不滚，但未解释舵机没转。记录是哪几个角不变，急停后看 `steer_stall_mask_`、`alignment_at_stall_`。没有堵转锁存不代表没问题：指令没到 8000 raw、反复换向或未持续 500 ms 都可能不触发。用下文的 ID 2 探针或只读 CAN 记录判别实际发送。 |
| 舵轮确实在转，但一直有同一位不清 | 对这一轮比较 `s_steers[i].angle_`、目标角与最终目标。若角误差越转越大，优先查 `kSteerDir` 和反馈是否属于这只轮；物理朝向到位、数学角不对，查 `kSteerAngleOffset`。误差往正确方向缩小才考虑舵 PID 或目标变化率。 |
| 对齐位为 0、`s_wheel_frame` 有持续非零命令，但一轮或多轮轮胎不滚 | 在底盘 CAN2 只读确认 M3508 `0x200`、各自反馈 `0x201`～`0x204` 和对应轮速 `vel_`；核对哪段字节对应停住的轮。可与同车正常固件比帧。轮胎不滚不能直接归咎于舵门或轮速 PID。 |
| 中位还有一只轮胎持续主动转，或推杆方向和实际明显相反 | 马上急停，继续有驱动力就切断驱动电源。核对零杆时 `lv/lh/wheel`、`ramped_` 与四轮电流，再区分残留命令、轮位映射、方向或机械惯性。不要回退到旧逐轮放行来恢复响应。 |

探针只用于固定架空台架，按 [`docs/22` §4](22-舵轮回归修复与台架核对.md#4-若有舵向命令却无反馈变化可用独立的-id-2-探针) 先测 ID 2 电压帧。`attempted=0` 查触发条件；`attempted>0` 但 `queued=0` 查提交；`queued>0` 但 `sent=0` 查发送完成；`sent>0` 仍需对照 `peak_delta_a`、`peak_angle_rad`。一次小脉冲没动不能断定电机坏或模式错误。若 ID 2 与异常轮不是同一只，探针结果也不能替其他三只轮作证。如果队友再次上车，用只读 CAN 对比他已正常运行时的 `0x1FF` 或 `0x1FE`、DLC、哪两个字节非零及对应反馈；确认模式差异后再改软件。**不用改队里的电机设置。**

## 能动以后才有的分支

| 现象 | 应对 |
|---|---|
| 四轮架空方向看起来不一样 | 舵向相差 180°且轮速取反是合法等效解。结合四轮的**有符号滚动方向**，再决定改不改 `kWheelDir`。单个物理轮与索引不符才核对 `kWheelId/kSteerId`；对应关系确认后改底盘。 |
| 云台左偏，推前进却向车头或右方走 | 先看 `peer_input_.yaw_joint`：中位应近零，向车体左转应为正；再看 `s_solver.chassis_motion_.vx/vy`。反馈错查 Yaw 的 ID、方向、零点和量程；反馈对、换算错再查坐标旋转，不能照旧 PDF 公式盲翻符号。 |
| 跟随时零杆车也转 | 云台和车头存在夹角时，这是跟随功能。架空固定的底盘无法追上云台，只看轮组是否产生缩小夹角的趋势。受控落地时若越转越偏，先查 Yaw 正方向与底盘陀螺轴；方向正确但过冲才调 `kFollowKp/kFollowKd`。 |
| 小陀螺松杆仍转、拨轮过中位突然反向 | 该档拨轮中位仍请求 1.5 rad/s；当前满范围到 6 rad/s。退出先急停再切档。不要从满拨开始试；场地或队员认为起调转速偏高时，提前下调 `kMinSpinW/kMaxSpinW` 并重新构建底盘；不把最低值改成 0 当验收行为。 |
| 云台不动、掉力、乱甩或 Pitch 接近限位 | 若 Yaw/Pitch 故障或发热先急停、切驱动动力并记录达妙 `dm_status_`；故障锁存不靠切拨杆自动清除。核对修正图 DMJ620 与实际铭牌、已配置的 MIT 三量程。方向和量程确认后，再测机械行程和零点；Pitch 需要同步调整底盘目标限位和云台执行限位，不能只改一板放宽。 |
| 能走但抖、响应慢、输出饱和或发热 | 先排轮位、方向、零点、反馈断续、机械卡滞。舵角先调、再轮速、再调云台和跟随外环。每次只改一个原因对应的一组参数，保留前后记录；发热或持续饱和不靠增加电压/电流解决。 |
| 分离单向运动正常，急转或小陀螺加平移时驱动断续 | 对比 `align_blocked_mask_` 与 `s_solver.command_[i]` 的 `angle/desired_angle/speed`。若多轮只在目标骤变时反复等待，先用较低速度和较平顺输入复测；同一轮持续落后则查那一轮执行。不要把快速换向与一直不放行混为一谈。 |
| 解除急停没有统一舵向回中 | 当前固件原本就没有主动回中。按第 3.5 节属于待解决的验收项，同时考核红线规定未进 Working 输出归零；验收前与队里确认允许的触发时点，不把上电自行转动临时加进去。 |
| 遥控关闭后没有立即静止 | 先看是否仍有**主动驱动力**；软件零输入与惯性停转分开计时。还有主动驱动就切动力，停止试车。只有前面架空确认正常，才跟队员按 [`docs/08`](08-台架故障注入清单.md) 实测急停、遥控失联、板间故障与看门狗，不在落地运动时故意断链路。 |

若到场时间有限，第一轮只求拿到两个结论：**两板能否稳定 `kWorking`；分离模式第一次小推杆时，四个舵角是否实际变化。** 第一个问题不过，就不用试三模式；第二个不过，留一次有效的 CAN／角度记录比换 PID 或反复烧录更有价值。
