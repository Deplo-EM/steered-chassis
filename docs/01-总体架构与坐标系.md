# 01 · 总体架构与坐标系

> 这篇解决三个问题：**一条指令是怎么从摇杆走到轮子的**、**坐标系和符号到底怎么定的**、
> **两块板每 1ms 各自在忙什么**。

---

## 1. 一条指令的旅程

```
 操作手推动左摇杆
        │
        ▼
 ┌──────────────┐   USART3 18字节    ┌──────────────────┐
 │ DT7 遥控器    │ ─────────────────▶ │ 底盘板 DBUS 解码  │
 └──────────────┘   (100Hz, 中断)     └────────┬─────────┘
                                              │ 摇杆值 ∈ [-1,1]
                                              ▼
                                    ┌──────────────────────┐
                                    │ 底盘板 Robot          │
                                    │ 1) 选模式(分离/跟随/小陀螺)
                                    │ 2) 摇杆 → (vx,vy,w)   │ ← 云台坐标系！
                                    │ 3) 加速度限幅          │
                                    └───────┬──────────────┘
                                            │ (vx,vy,w) + δ
                                            ▼
                                    ┌──────────────────────┐
                                    │ Chassis 底盘模块      │
                                    │ 4) 云台系 → 车体系    │
                                    │ 5) 逆解 → 4× (舵角,轮速)
                                    │ 6) 舵角环 → GM6020 电压
                                    │ 7) 轮速环 → M3508 电流│
                                    └───────┬──────────────┘
                                            │ setInput()
                                            ▼
                                      8 个底盘电机

 ── 同时，云台那条线 ─────────────────────────────────────────

 底盘板 Robot ──C2G 0x210──▶ 云台板 Robot ──▶ Gimbal 模块 ──▶ yaw/pitch 达妙
   (yaw转速设定)              (积分成世界目标)   (角度误差→力矩)
       ▲                                              │
       └──────────── G2C 0x211（实际关节角 = δ）◀──────┘
```

**为什么 δ 要绕一圈从云台板回来？** 因为 δ 是「云台相对车头」的夹角，它的测量值在云台板的
yaw 电机反馈里。底盘板必须拿到它，才能把「操作手心里的前进方向」换算成「车体坐标下的速度」。

## 2. 坐标系与符号约定（全工程统一）

> 这一节是整份代码的地基。符号搞反，车会原地打转或者倒着走，而且现象很迷惑。

### 2.1 三套坐标系

| 坐标系 | x 轴 | y 轴 | z 轴 | 谁在用 |
|---|---|---|---|---|
| 世界系（惯性系） | 上电瞬间车头方向 | 左手边 | 向上 | IMU 的 yaw、云台世界目标 |
| 车体系 | 车头方向 | 车左手边 | 向上 | 逆解、轮组位置 |
| 云台系 | 枪口方向 | 枪口左手边 | 向上 | 遥控器摇杆映射出的 (vx, vy) |

三者都是**右手系**：从上方俯视，**逆时针为正**。

### 2.2 δ 的定义

```
δ = 云台朝向 − 车头朝向      （从车头 +x 转到枪口 +x 的角度，逆时针为正）

     车头 +x
        ╲  δ
         ╲╱
         ╱
        ╱  枪口 +x
```

- δ > 0：枪口在车头**左边**
- δ < 0：枪口在车头**右边**
- δ = 0：车头正对枪口（跟随模式的目标状态）

### 2.3 为什么 δ 恰好等于 yaw 电机的关节角

因为 yaw 电机的**定子固定在底盘上、转子带着云台**，它测的机械角度就是「云台相对底盘转了多少」，
也就是 δ。前提是：

1. 云台做**世界系稳定**（见下一节），否则 δ 不会随底盘转动而变化；
2. yaw 关节零点标定成「枪口与车头对齐时 δ=0」（否则差一个常数，用 `kYawJointOffset` 补）。

### 2.4 云台系 → 车体系的旋转

设某速度在云台系是 (vx, vy)，在车体系是 (vx', vy')，δ = 云台朝向 − 车头朝向（逆时针为正）。
推导只要三步：

**第 1 步**：云台系的两个基向量，在车体系里分别是

```
x_云台 = ( cosδ,  sinδ)     ← 枪口方向
y_云台 = (−sinδ,  cosδ)     ← 枪口左边
```

**第 2 步**：一个物理向量在云台系里是 (vx, vy)，意思是
`v = vx·x_云台 + vy·y_云台`。

**第 3 步**：把基向量代进去，就得到它在车体系里的坐标：

```
vx' = vx·cosδ − vy·sinδ
vy' = vx·sinδ + vy·cosδ
```

**直觉检验**（这一步一定要做，符号错就是在这里露馅的）：

> 枪口在车头左边 90°（δ = +90°），操作手推「前进」。
> 云端系 (1, 0) → 车体系 (cos90°, sin90°) = **(0, +1)** = 车体左侧。
> 车往左走 —— 对，因为枪口就在左边，沿枪口方向走就是往左。

> ⚠️ **考核说明 3.2 印的公式是反的**
> 它给的是 `vx' = vx·cosδ + vy·sinδ`、`vy' = −vx·sinδ + vy·cosδ`，也就是 R(−δ)，
> 与它自己「δ = 云台朝向 − 车头朝向」的定义差一个符号。
> 用那个式子，上面这个例子会算出 (0, −1)：枪口朝左、车却往右跑。
> 这不是纸上谈兵——现场「转云台再推杆」一眼就能看见。
>
> 本工程按物理正确性实现 R(+δ)，代码只在 `chassis_ik_solver.cpp` 第 1 步出现一次，
> 并由单测的两个用例锁定：
> 1. 「云台在车头左侧 90° → 车往左平移」；
> 2. 「小陀螺：底盘转 θ，车体系速度转 θ，转回世界系仍是原方向」。
>
> 🔧 如果实车因为 IMU / 电机装反而发现左右反了：把那里的两个 sin 项符号同时取反，
> 并同步改单测期望值即可，其它地方一律不用动。

### 2.5 关键符号速查

| 量 | 正方向 | 单位 |
|---|---|---|
| 摇杆 `rc_lv` | 上推为正 | [-1,1] |
| 摇杆 `rc_lh` | 右推为正 | [-1,1] |
| `vx` | 枪口方向为正 | m/s |
| `vy` | 枪口左侧为正 | m/s |
| `w` | 逆时针（俯视）为正 | rad/s |
| 舵角 `angle` | 车体 +x 起，逆时针为正 | rad |
| `yaw`（IMU/云台） | 逆时针为正 | rad |
| `pitch` | 枪口抬高为正（由 `kPitchStickSign` 标定） | rad |

## 3. 为什么云台 yaw 必须做「世界系稳定」

这是整个设计里最容易想错的地方，单独讲一遍。

### 3.1 只做关节角闭环会怎样

假设云台只控制「相对底盘的夹角 j」：

```
底盘转 30°  →  云台跟着转 30°（因为电机把 j 锁死了）→  枪口在世界里也转了 30°
```

于是：

- 操作手松开摇杆，枪口会随车头乱转（打不准）；
- 「跟随模式」要求车头去追枪口，可枪口又被车头带着转 → j 永远不变 → **永远追不上**，
  底盘会以恒定角速度一直转下去。

### 3.2 世界系稳定怎么解决

云台的 IMU 装在枪管上，能测出枪口在世界里的朝向 ψ。控制器改为：

```
误差 = ψ目标 − ψ实测        →  PID  →  力矩
```

底盘怎么转都不影响 ψ目标。底盘转 30°，yaw 电机自动反向补 30°，枪口在世界里纹丝不动。
而这时关节角 j 恰好变成了 30° —— 正是底盘板需要的 δ。

```
      δ = 0                       底盘转 30°，云台反向补 30°
   车头↑枪口                      车头↗  枪口↑
    └─┴─┘                          └────┴─┘
                                   δ = 30°
```

### 3.3 为什么「目标」只能由云台板自己积分

「世界角」是相对**某块板的 IMU 上电姿态**定义的。底盘板的 IMU 和云台板的 IMU 各有一个零点，
两者差一个未知常数。所以底盘板没法直接告诉云台板「你该转到世界角 X 度」。
能跨板传递的只有**相对量**：角速度。

于是分工变成：底盘板说「转多快」，云台板自己积分成目标角并闭环。这就是 C2G 帧里
`yaw_rate` 而不是 `yaw_target` 的原因（详见 `docs/03`）。

## 4. 两块板的 1ms 时序

### 4.1 底盘板

```
TIM6 中断（1kHz，优先级 3）
 └─ MainTask()  ── Robot::update()
     ① imu->update()        读 BMI088（SPI）→ 扣零漂 → Mahony → 欧拉角
     ② updateInput()        读左右拨杆：模式、急停
     ③ updateStateMachine() Dead / Resurrection / Working 迁移
     ④ applyOutput()
          ├─ 非 Working 或 急停 → chassis->stop()（全部 setInput(0)）
          └─ Working →
               generateCommand()      摇杆→(vx,vy,w)、加速度限幅、云台指令
               chassis->setMotion()
               chassis->update()      逆解 + 4×舵角环 + 4×轮速环 + setInput
     ⑤ updateCommData()     把本板状态写进 C2G 数据（不发送）
 └─ CommTask()
     ① 4×M3508 → 合并成一帧 0x200 → CAN2（500Hz）
     ② 4×GM6020 → 合并成一帧 0x1FF → CAN1（500Hz）
     ③ C2G 帧 0x210 → CAN2（200Hz，关键状态变化立即发）
     ④ 条件喂狗
```

### 4.2 云台板

```
TIM6 中断（1kHz，优先级 3）
 └─ MainTask() ── Robot::update()
     ① imu->update()
     ② updateInput()        本地急停 + 底盘帧里的急停
     ③ updateStateMachine() 条件：底盘帧在线 + IMU 标定完成 + 两电机有反馈
     ④ applyOutput()
          ├─ 未使能/急停 → gimbal->stop()
          └─ 使能 →
               使能上升沿：目标对齐当前角度（无扰切换）
               yaw目标 += yaw_rate × dt
               pitch目标 = 底盘下发的关节角
               gimbal->update()   2× 位置环 → 力矩 → setInput
     ⑤ updateCommData()     回填 G2C（实际关节角 = δ）
 └─ CommTask()
     ① yaw 帧 → CAN1（共享板间总线，500Hz）
     ② pitch 帧 → CAN2（500Hz）
     ③ G2C 帧 0x211 → CAN1
```

> 注意：**控制在前、通信在后**。本周期算出来的指令，同一周期就发出去了，不会多等 1ms。
> 中断里不做任何阻塞操作（SPI 读 IMU 除外，约几十微秒）。

## 5. 状态机

两板结构相同，进入条件不同：

```
        ┌────────────────────────────────────────────┐
        │                                            │
        ▼                                            │
   ┌─────────┐   条件全满足    ┌──────────────┐  500ms  ┌─────────┐
   │  Dead   │ ─────────────▶ │ Resurrection │ ──────▶ │ Working │
   │ 输出全0 │ ◀───────────── │  输出全0      │ ◀────── │ 正常控制 │
   └─────────┘   条件丢失      └──────────────┘  条件丢失 └─────────┘
```

| 条件 | 底盘板 | 云台板 |
|---|---|---|
| 遥控器在线 | ✅（本板 DBUS 100ms 内有帧） | 不要求（接收机可能不在这块板） |
| 对方板在线 | ✅（且对方必须已 Working） | ✅（只看帧是否在来） |
| IMU 零漂标定完成 | ✅ | ✅ |
| 电机全部有反馈 | ✅ 8 个 | ✅ 2 个 |

- **Dead**：输出全零等条件，什么都不做。
- **Resurrection**：等 500ms，让状态稳定；**全程输出为 0**（不做舵角回中——那属于无人下达的运动指令，见 docs/05）。
- **Working**：正常控制。

**任何一项条件丢失，立刻退回 Dead 并归零输出**——不做「再等一会儿看看」的宽容处理。
宁可误停，不可失控。
