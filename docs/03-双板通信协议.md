# 03 · 双板通信协议

> 两块单片机之间唯一的联系就是 CAN 总线上的 8 个字节。这篇讲：装什么、为什么这么装、
> 怎么保证对面读到的是对的。

---

## 1. 为什么需要这一层

```
   ┌──────────────┐                        ┌──────────────┐
   │   底盘板      │   8 字节 CAN 帧        │   云台板      │
   │  (一台MCU)    │ ◀────────────────────▶ │  (另一台MCU)  │
   └──────────────┘   0x210 / 0x211        └──────────────┘
```

两台 MCU **各有各的内存、各跑各的固件**，函数不能互调、变量不能共享。
所以任何要传递的信息，都必须先"压扁"成字节，发过去再"展开"。

这一层负责三件事：

1. `encode()`：把己方的语义结构体打包成 8 字节；
2. `decode()`：把对面 8 字节还原成语义，并刷新"对方还活着"的时间戳；
3. `isOffline()`：超过阈值没收到新帧 → 判定对方掉线。

## 2. 帧格式（8 字节定长，收发严格对称）

### 2.1 底盘 → 云台（C2G，标准帧 `0x210`）

| 字节 | 内容 | 类型 | 单位 / 范围 |
|---|---|---|---|
| 0 | 标志位（见下表） | uint8 | — |
| 1~2 | `yaw_rate_cmd` | int16 大端 | 0.001 rad/s，±32.7 |
| 3~4 | `pitch_target` | int16 大端 | 0.0001 rad，±3.27 |
| 5 | 保留（填 0） | uint8 | — |
| 6 | 序号 `seq`（每帧 +1） | uint8 | 0~255 回绕 |
| 7 | CRC8（对字节 0~6） | uint8 | 多项式 0x07 |

标志位 byte0：

| bit | 含义 | 谁用 |
|---|---|---|
| 0 | `alive` 本板已初始化 | 云台 |
| 1 | `working` 本板处于 Working | 云台 |
| 2 | `estop` 急停 | 云台（立即停） |
| 3 | `dbus_online` 本板遥控器在线 | 云台（喂狗依据） |
| 4~5 | `mode` 底盘模式（0 分离 / 1 跟随 / 2 小陀螺） | 云台（调试/显示） |
| 6 | `imu_ready` 本板 IMU 标定完成 | 云台 |
| 7 | `gimbal_enable` 允许云台出力 | 云台（**关键**） |

### 2.2 云台 → 底盘（G2C，标准帧 `0x211`）

| 字节 | 内容 | 类型 | 单位 / 范围 |
|---|---|---|---|
| 0 | 标志位 | uint8 | — |
| 1~2 | `yaw_joint` 实际 yaw 关节角（= δ） | int16 大端 | 0.0001 rad |
| 3~4 | `pitch_joint` 实际 pitch 关节角 | int16 大端 | 0.0001 rad |
| 5 | 保留 | uint8 | — |
| 6 | 序号 | uint8 | — |
| 7 | CRC8 | uint8 | — |

标志位 byte0：

| bit | 含义 |
|---|---|
| 0 | `alive` |
| 1 | `working` 云台已进入 Working（底盘用它做准入条件） |
| 2 | `estop` 云台本地判定急停 |
| 3 | `dbus_online` 云台板遥控器在线 |
| 4 | `imu_ready` |
| 5 | `pitch_at_limit` pitch 顶到软件限位 |
| 6~7 | 保留 |

## 3. 为什么 yaw 下发"角速度"而不是"角度"

这是本协议里最值得讲的一个设计决定。考核说明 3.5 的字段清单里写的是
"底盘期望的云台 yaw/pitch 目标"，我们只对 pitch 下发角度，yaw 下发转速，原因是物理限制：

### 3.1 云台 yaw 的世界角只有它自己知道

- "世界角"是相对**某块板 IMU 上电那一刻**的姿态定义的；
- 底盘板的 IMU 和云台板的 IMU 各有一个零点，两者差一个**未知常数**；
- 所以底盘板无法表达"你该转到世界角 37°"——它说的 37° 和云台板说的 37° 不是同一个方向。

### 3.2 关节角也不能下发

有人会想："那下发关节角总行了吧，关节角是相对量。"
不行——如果云台只追关节角，底盘一转，云台就被带着转（前面 `docs/01` 第 3 节详细讲过），
跟随模式永远收敛不了。

### 3.3 结论

| 量 | 能跨板传吗 | 做法 |
|---|---|---|
| 世界角目标 | ❌ 两板零点不同 | — |
| 关节角目标 | ⚠️ 能传，但会让云台跟着车头转 | 只用于 pitch |
| **角速度** | ✅ 纯相对量，与零点无关 | **yaw 用这个**，云台自己积分 |

所以：**底盘板说"转多快"，云台板自己积分成世界目标并闭环**。
这也是为什么云台板 `robot.cpp` 里有 `yaw_target_world_ += yaw_rate * dt` 这一行。

## 4. 缩放：为什么用定点整数

CAN 一帧只有 8 字节，浮点要 4 字节一个，装不下两个角度 + 标志。

做法：**乘以一个固定比例，四舍五入成 int16**。

| 量 | 比例 | 分辨率 | 量程 |
|---|---|---|---|
| 角度 | ×10000 | 0.0001 rad ≈ 0.0057° | ±3.2767 rad |
| 角速度 | ×1000 | 0.001 rad/s | ±32.767 rad/s |

三个要点：

1. **收发两端比例必须完全一致**，否则数值会差 10 倍、100 倍——而且看起来"像正常的数"，
   极难排查。比例定义在 `gimbal_chassis_comm.cpp` 的匿名命名空间里，只此一处。
2. **要限幅**：`FloatToInt16` 把超范围的值夹到 ±32767，避免 `lroundf` 溢出（C++ 里是未定义行为）。
3. **下界用 −32767 不用 −32768**：保持对称，也避免取反溢出。

## 5. 为什么还要加 CRC8

CAN 链路层本来就有 15 位 CRC，为什么帧里再加一个？

- CAN 的 CRC 保护的是**总线传输**；它不能防止"发送方自己 encode 错了"或"接收方解析偏了"；
- 一个字节的偏移错误会让 yaw 和 pitch 互相串位，数据看起来仍然"合理"（都在 ±3 rad 内），
  状态机不会发现，车会突然乱动；
- 加 1 字节 CRC8 后，**任何一位翻转都会整帧丢弃**，并且不刷新在线时间戳，
  行为退化成"丢了一帧"，而不是"收到一帧垃圾"。

实现直接用了骨架里提供的 `crc8.hpp`（查表法，多项式 0x07）。

## 6. 离线判定

```cpp
bool isOffline() const {
    if (!received_) return true;                 // 上电后一帧都没收到
    return (GetTickMs() - last_rx_tick_) > 100;  // 超过 100ms
}
```

三个细节：

- **`received_` 标志**：不能只用时间差，因为刚上电时 `last_rx_tick_` 是构造时刻，
  前 100ms 会误判为"在线"；
- **无符号减法**：`GetTickMs()` 约 49.7 天回绕一次，无符号减法在回绕时结果依然正确；
- **阈值 100ms**：帧率 1kHz，100ms = 连续丢 100 帧，足够排除偶发丢帧，又不至于反应太慢。

## 7. 收发时序

```
底盘板                                  云台板
  │                                       │
  │  ── CommTask: encode → 0x210 ──────▶  │  CAN1 接收中断
  │                                       │   ├─ CRC 校验
  │                                       │   ├─ 更新 last_rx_tick_
  │                                       │   └─ （若 dbus_online）喂狗
  │                                       │
  │  ◀──── CommTask: encode ← 0x211 ────  │
  │  CAN1 接收中断                         │
  │   ├─ CRC 校验                          │
  │   ├─ 更新 last_rx_tick_                │
  │   └─ 底盘 Robot 下一周期读到新的 yaw_joint
```

- 两板都是 **1kHz** 发帧；
- 接收在**中断**里（要快），解码后的数据在**下一周期**被控制逻辑读取（1ms 延迟，可接受）；
- 发送在 `CommTask` 里，与控制计算同周期。

## 8. 自测（`tests/test_main.cpp`）

| 用例 | 验证什么 |
|---|---|
| 底盘 → 云台 encode→decode | 字段、标志位、模式全部还原 |
| 云台 → 底盘 encode→decode | 同上 |
| 篡改一字节 | CRC 拦截，数据不变 |
| 没收到过帧 | `isOffline() == true` |
| 两板 tx/rx 互补 | `chassis.tx == gimbal.rx` 且 `chassis.rx == gimbal.tx` |

改完协议**先跑单测**：它能抓住 90% 的"偏移写错一位"的问题。

## 9. 常见错误对照

| 现象 | 原因 |
|---|---|
| 云台朝一个方向慢慢转不停 | yaw_rate 符号反了，或云台没做世界系稳定 |
| 车一推杆就斜着走 | `yaw_joint` 缩放比例两边不一致（比如一边 ×10000 一边 ×1000） |
| 两板都正常但车不动 | `gimbal_enable` 一直是 0（底盘板没进 Working / 云台板没 Working） |
| 偶尔抽一下 | CRC 一直失败 → 检查字节序（本项目统一大端） |
| 关遥控器后只有一块板复位 | 喂狗路径不一致，检查 `comm_task.cpp` 与 `Gimbal/src/HW_can.cpp` |
