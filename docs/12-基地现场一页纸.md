# 12 · 已装配整车：烧录、起动和三种模式的手把手教程

> 最新接线、正常固件和舵轮故障定位以 [11-14 台架核对](22-舵轮回归修复与台架核对.md) 为准。底盘和云台须配套烧录，探针固件只用于固定台架。

适用：整车已经装好，电机ID和达妙MIT模式已由队员配置。只验证**分离、跟随、小陀螺**，不涉及发射机构。
本教程2026-11-11纠正为**Ozone主流程**；代码修复日期2026-11-10，基于审计`2eee2a6`完成本轮修复。原始发现见`docs/13`、修复记录与硬件待验项见`docs/15`，全部现场参数见`docs/14`。
第一次通电请熟悉配电与急停的队员在旁协助；本教程不是实车安全验收证明。

## 0. 先记四句话

- **编译**只把代码变成电脑上的固件文件；**烧录**才会改变板子里的程序。
- 底盘和云台各烧一份不同固件。三种模式用拨杆切换，不需要为换模式重烧。
- Working只表示程序准入条件满足；还要解除急停才能出力。灯亮不能证明Working。
- 正常情况下先烧配套固件、核对起动条件；不要一到现场就改PID。需要整定时按[Ozone PID详细教程](17-Ozone中PID整定详细教程.md)，先录原参数基线。

只跑三种底盘模式，也仍需两板、四个驱动电机、四个转向电机、两个云台电机和双板CAN。
**不能拔掉云台**：底盘依赖它的朝向与就绪反馈。没有全部电机时停在Dead是设计要求。

**当前未实现上电主动舵向回中。**底盘零指令保持实测舵角，云台进入控制时先对齐当前姿态；这不等于任务书中的恢复自检舵向回中，仍是未闭合验收项。有没有回中不能代替Running/Working检查。

## 1. 不上电，先准备

1. 让队员指出哪块是底盘板、哪块是云台板，贴好标签。
2. 用稳固支架把四轮架空并固定车架；轮胎与支架留空间。禁止用手扶运行的车固定它。
3. 清空云台转动范围。先确认线缆/滑环是否允许连续yaw旋转；软件能连续转不代表线缆能。
4. 让队员指出驱动电源的切断位置。遥控急停不起作用时立即切断驱动电源。
5. 两摇杆、拨轮回中；左拨杆先放上档（分离），右拨杆放下档（急停）。

整车已装配，只核对现有插头和标签，不必把所有线拆下来重接。软件默认：

| 对象 | 软件要求 |
|---|---|
| 接收机DBUS | 修正图接云台 USART3，经 `0x212`～`0x214` 转发；软件仍支持底盘本地 USART3。首次必须右下急停确认来源 |
| M3508驱动轮 | 底盘CAN2，ID 1/2/3/4 |
| GM6020转向电机 | 底盘CAN1，ID 1/2/3/4 |
| 两板互连 | 底盘 CAN2 ↔ 云台 CAN1（以修正图为准，集中配置见 `board_wiring.hpp`） |
| 达妙 yaw/pitch | 修正图标注 DMJ620；yaw 发送走云台 CAN1（与底盘 CAN2 共线），pitch 走云台 CAN2。发送 ID 1/2，固件期望反馈 ID `0x11`/`0x12`；MIT 量程仍待核对 |

## 2. 电脑上先准备：仍用Ozone

继续使用以前调试时的**Ozone和原有探针**。Ozone是电脑上的烧录/调试软件；J-Link是连接电脑与控制板的硬件。
不需要因为本轮代码修复改用OpenOCD或GDB。只有现场明确选择ST-Link路线时才读[备用流程](16-OpenOCD与GDB备用流程.md)。

本机安装路径是`C:/Program Files/SEGGER/Ozone/Ozone.exe`，已核对版本3.26；两份新工程按本机官方手册配置。
它们不绑定以前F103工程的探针序列号；目标改为本项目的**STM32F407IG / Cortex-M4 / SWD / 1 MHz**。
沿用队里已经正常工作的、受支持的探针配置；有多只探针时在Ozone中按实际序列号选择，不能随便选第一只。

### 2.1 先核对五个文件

按`Win+R`，输入`powershell`回车，复制整块：

```powershell
$ProjectRoot = 'D:/ForTest/steered_skeleton/steered_skeleton'
Set-Location -LiteralPath $ProjectRoot
Test-Path 'C:/Program Files/SEGGER/Ozone/Ozone.exe'
Test-Path "$ProjectRoot/debug/ozone/chassis.jdebug"
Test-Path "$ProjectRoot/debug/ozone/gimbal.jdebug"
Test-Path "$ProjectRoot/Chassis/build/steered_chassis.elf"
Test-Path "$ProjectRoot/Gimbal/build/steered_gimbal.elf"
```

应看到**5个True**。有False先查路径或构建结果；换电脑时改本机路径。
`.jdebug`是Ozone工程配置，`.elf`才是要烧进板子的固件，二者不能混淆。
两份工程使用相对路径指向下面的ELF，保留仓库目录结构即可；不要打开以前的`HW1.jdebug`、`final_speed.jdebug`或骨架旧`build/Debug`产物。

| 要操作的板 | 在Ozone打开的工程 | 它加载的固件 |
|---|---|---|
| 底盘 | `debug/ozone/chassis.jdebug` | `Chassis/build/steered_chassis.elf` |
| 云台 | `debug/ozone/gimbal.jdebug` | `Gimbal/build/steered_gimbal.elf` |

### 2.2 改过代码时先编译

Ozone负责加载/下载/观察，**不会代替CMake编译你的改动**。没有改代码可用已核对的配套ELF。
需要重编时，在刚才窗口执行：

```powershell
cmake -S Chassis -B Chassis/build/audit -G Ninja -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw '底盘配置失败，停止' }
cmake --build Chassis/build/audit
if ($LASTEXITCODE -ne 0) { throw '底盘编译失败，停止' }
cmake -S Gimbal -B Gimbal/build/audit -G Ninja -DCMAKE_BUILD_TYPE=Debug
if ($LASTEXITCODE -ne 0) { throw '云台配置失败，停止' }
cmake --build Gimbal/build/audit
if ($LASTEXITCODE -ne 0) { throw '云台编译失败，停止' }
```

找不到cmake、Ninja或ARM编译器时，请队员恢复工具链，不要改源码处理环境问题。
出现编译error时不能继续烧旧ELF冒充新版本。重编成功后在Ozone重新加载对应ELF/重新打开对应工程；
仅看到“文件已改变”提示或源代码新内容，不代表芯片里的固件已经更新。

## 3. 用Ozone烧录：一次一块板

### 3.1 接线与隔离驱动力

让队员隔离电机驱动电源，只给待烧的控制板按规定供电，一次只接一块板。
按**现用探针和C板手册**核对SWDIO、SWCLK、GND、VTref/目标电压参考以及需要的NRST。
不要把VTref默认当供电输出，也不要照着“3V3对3V3”并接两路电源。
不认识针脚让队员核对，不沿用其他型号蓝板的接线表。

### 3.2 底盘板：照着点

1. 确认探针实际接的是**底盘板**，驱动力仍隔离。先开遥控器，右拨杆下档急停、摇杆和拨轮回中；本工程下载后会立即运行程序。
2. 打开Ozone。点`File → Open`，选择仓库里的`debug/ozone/chassis.jdebug`。
3. 工程打开只加载电脑上的文件，不会自动连接、下载或运行。本次Debug构建已显式使用DWARF4，减少Ozone3.26解析DWARF5的兼容问题。核对程序文件是`Chassis/build/steered_chassis.elf`，目标是`STM32F407IG`，接口`SWD`。
4. 本机3.26的探针设置在`Tools → J-Link Settings`，也可用`Ctrl+Alt+J`。确认USB、正确探针；初始SWD速度1 MHz，先不要为了更快改到很高。
5. 打开`Tools → System Variables`（`Ctrl+Alt+V`；不同版本也可能位于Edit），确认`VAR_VERIFY_DOWNLOAD=1`，即下载后读回比较。本工程已设置它。
6. 点`Debug → Start Debugging`（有些版本显示`Start Debug Session`）的下拉项，选择**`Download & Reset Program`**。这是“把这份新程序写入板子”，不要选Attach代替。
7. 查看Console/下载日志：下载完成、没有下载或校验失败。若版本显示校验结果，必须成功；只有灯亮、文件打开或没有弹窗不能证明烧录成功。无法确认校验时停下请队员核对日志，不做运动试验。
8. 本工程现设为**`Reset & Run`**：下载/校验后复位并运行。必须看Ozone显示**Running**；若仍是**Halted/Stopped**，保持驱动力隔离和遥控急停，点`Debug → Continue`，直到Running。不要反复Reset；不要停在main或复位入口就推杆。
9. 再观察`uwTick`和`robot::diag::g_cpu.cycle_count`是否持续增长。Running表示CPU在执行；Working表示本项目准入条件满足；解除急停后才允许电机控制。这是三个不同条件。
10. 当前只烧单板/驱动力隔离时，缺反馈而Dead是预期，不能据此修改PID。若只做烧录，校验完成后结束会话、断电换板；后续两板恢复正常接线并按第4节重新上电。

**F5会随当前状态执行“开始会话”或“继续运行”**，新手以菜单文字为准，不连续盲按F5。
更新.jdebug文件不会自动改变已经打开的旧会话；先在隔离驱动力条件下结束旧会话，重新打开对应工程，再确认复位方式为Reset & Run。
若仍存在普通断点/数据断点，程序也可能再次停下；受控停机后清除本次运动试验不需要的断点，不能在运动中用暂停来采样。

### 3.3 云台板

控制板断电后把探针换到**云台板**，重新按规定供电。重复第3.2节，唯一必须换的是：

- 打开`debug/ozone/gimbal.jdebug`。
- 核对程序文件是`Gimbal/build/steered_gimbal.elf`。
- 同样选择`Download & Reset Program`并检查下载/校验。

两板完成后断电、拔调试器，让队员恢复整车正常连接；从第4节重新完成遥控急停确认和上电。
**不要直接复用旧调试会话的“继续运行”当作一次正常整车起动。**

| 报错/现象 | 先处理什么 |
|---|---|
| ELF找不到 | 回第2节；编译成功后确认实际路径，不改成旧Debug产物 |
| J-Link找不到/连接被占用 | USB、探针供电、驱动，关闭占用同一探针的其他调试会话 |
| 能找到探针但目标连不上 | C板供电、电压参考、共地、SWD/NRST，由队员核对 |
| 反复复位难连接 | 保持驱动力隔离，请队员处理复位连接；不关看门狗保护来“修好” |
| 下载/校验失败 | 停止运动试验，查供电、线缆、设备型号与日志，不把加载文件当下载成功 |
| 源码找不到或变量无法解析 | 先核对ELF与本次源码匹配；旧Ozone不识别调试信息时记录错误交队员处理，不靠修改电机代码消除 |
| 两板可能烧反 | 隔离驱动力，按标签重新下载正确文件，不用推杆判断 |

## 4. 起动：这一步漏了，车就不动

1. 四轮仍架空、车架固定，云台范围无人接触。
2. 左拨杆上档（分离），右拨杆下档（急停），摇杆和拨轮全回中。
3. **先开遥控器，再给整车上电。**
4. 若连接Ozone，先看状态：必须是**Running**。若是Halted/Stopped，保持急停并先隔离驱动力，点`Debug → Continue`恢复运行，再由队员按规程恢复供电/接线；不能停着CPU直接推杆。只Attach一个已暂停程序也不会自动让它运行。
5. 保持急停，车与云台静止至少3秒。IMU要累计2000个有效样本，等满3秒本身不能证明就绪；若CPU计数不增长，继续等没有用。
6. 若出现持续驱动、甩动、异常声音，立即保持急停并切断驱动电源。
7. CPU持续运行、全体反馈正常并完成标定/自检后，确认没有异常，再把右拨杆从下档移到中档；其他杆继续回中。
8. 分离模式零杆应静止。若主动运动，立即回下档急停，查拨轮中位和遥控读数。

底盘上电及任何故障退回Dead后都会撤销授权，必须重新收到当前控制来源的有效急停档。
**正常档一直等待，不能代替急停确认。** 完全没反应先回急停，查第9节。
不要用手拨带电云台判断Working。

## 5. 遥控器速查

左右按软件`rc_l_switch`、`rc_r_switch`命名。若遥控器标签/左右识别不确定，先隔离驱动力，按第10节查原始拨杆值。

| 控件 | 位置/动作 | 作用 |
|---|---|---|
| 右拨杆 | **下** | 急停；保持下档一直停；也是一般掉线/CAN故障恢复确认；达妙故障另按断电流程 |
| 右拨杆 | 中/上 | 允许控制，但仍需全部准入条件 |
| 左拨杆 | **上** | 分离 |
| 左拨杆 | **中** | 跟随 |
| 左拨杆 | **下** | 小陀螺，解除急停就可能转 |
| 左摇杆 | 前后/左右 | 以云台方向为基准平移 |
| 右摇杆左右 | 小幅推 | 转云台yaw |
| 右摇杆上下 | 小幅推 | 改pitch目标，不需要时保持回中 |
| 拨轮，分离 | 偏转/回中 | 手动底盘旋转/零旋转 |
| 拨轮，小陀螺 | 偏转/回中 | 改自旋大小方向；**回中仍有1.5 rad/s自旋目标** |

三种模式下平移都看云台方向，不是“分离看车头、跟随才看云台”。

## 6. 架空，先验证分离，再检查急停

每次都“小幅推一下→回中→看”，异常先急停。

1. 左拨杆上档、拨轮回中，右拨杆从急停移到中档。
2. 左摇杆前推约5%～10%、约半秒，再回中；依次小幅后推、左推、右推。
3. 四轮应形成相同的目标平移方向。急变90°方向时应先转舵，再放开驱动。
4. 左杆回中，右摇杆轻推一点转云台，再回中。云台改变朝向，底盘不主动追齐。
5. 再给一点前进，轮组平移方向应跟随云台新朝向。
6. 小幅驱动时把右拨杆拨下急停。电机输入应撤销，轮胎可能因惯性继续转一段；若仍主动加速/顶住，切断驱动电源。

**看滚动方向，不只看轮子朝向。** 算法允许“舵轮约180°、驱动反转”，与“舵角0°、驱动正转”运动等效。
不能仅因轮子朝后就改Dir；确认朝向与带符号轮速合起来仍反向，才查电机方向。
架空只能核对轮组动作，不能证明车落地走直线。

## 7. 跟随模式

1. 先急停，摇杆、拨轮回中。
2. 左拨杆移中档，再解除急停。
3. 右摇杆轻推，让云台向左偏一点后松开。
4. 四轮应形成让底盘向左转、缩小车头与云台夹角的运动组合；云台向右偏应相反。
5. 左摇杆还能小幅平移，底盘一边移动一边追齐云台。

车固定在架子上时底盘不能转过去，**不能要求夹角收敛，更不能因此增大Kp**。
这里只短暂看运动趋势，然后急停；收敛和振荡在受控低速落地时检查。

## 8. 最后验证小陀螺

**所有摇杆回中也会自旋。** 当前目标1.5～6 rad/s不是对新手的安全速度保证。
场地不允许时先让队员按`docs/14`降低起调范围、重编重烧底盘。

1. 先急停，杆和拨轮回中，左拨杆下档。
2. 告诉旁人“准备自旋”，确认车架固定、线缆允许、无人接触。
3. 短暂解除急停，四轮应形成绕车体中心旋转的切线组合，然后急停。
4. 确认后才尝试一点平移组合，不把拨轮直接打满或突然反向。
5. 退出时先急停，再把左拨杆移回分离。仅松摇杆不能停转。

## 9. 满足架空检查后，才受控落地

由队员完成docs/08与docs/15所列的台架验证，并确认急停、机械限位、轮组方向和场地满足团队要求后进行。
尚未完成时，本节保留为待执行步骤，不能只因烧录成功或架空轮子会转就放行落地；新手不要独自开始。
每次切模式按：**急停→杆回中→选模式→确认区域→解除**。

| 顺序 | 手怎么动 | 应看到什么 |
|---|---|---|
| 分离 | 选分离，小幅前后/横移，回中 | 按云台方向平移；拨轮中位不主动自转 |
| 分离转云台 | 停车轻转云台，再给小幅前进 | 行进方向转向云台新朝向，底盘不主动追齐 |
| 跟随 | 急停下选跟随，解除后轻转云台 | 车头朝云台转，夹角逐渐减小 |
| 小陀螺 | 急停下选小陀螺，短暂解除后急停 | 底盘自旋；小幅平移仍总体以云台方向为准 |

保持小幅、短时，由小到大；具体速度和空场范围由现场决定。
振荡、撞限位、故障码、异常发热立即停。不能以“前面一直没坏”代替限位、温升和故障保护验收。

### 完全不动，按这个顺序查

0. **Ozone是否Running？**若Halted/Stopped，控制循环没执行，遥控无响应；先按第4节恢复运行，不能先调PID。
1. 两份固件是否烧对且下载/校验成功？
2. 上电后是否保持过有效急停？再保持约1秒，杆回中，选分离再试。
3. 当前遥控来源是否有新鲜合法帧？云台接收时，底盘本地DBUS计数为0可以正常；应看s_robot的remote_source_=kGimbal，以及comm_→remote_relay_→rx_frames_增长。
4. 两板和10台电机是否全上电、有反馈？缺一个会阻止底盘输出。
5. IMU是否初始化、标定、当次数据都正常？先查硬件，不直接放宽健康阈值。
6. CAN是否锁存？排除故障后在有效急停下连续通信监督通过超过100ms，再经过自检。
7. 达妙故障已锁存时，急停拨杆不能解除。保持急停、隔离驱动力，让队员排除过温/堵转/供电等根因，再按队里流程断开并恢复两板与电机电源，重新完成起动确认。禁止故障仍在时反复重启。
8. 反复重启时查电源、DBUS和CAN。遥控掉线的复位时间包含在线窗口和IWDG超时，不固定等于0.2秒。

## 10. 用Ozone看状态：先看变量，不执行目标函数

### 10.1 先分清三个连接选项

| Ozone菜单项 | 会做什么 | 什么时候用 |
|---|---|---|
| `Download & Reset Program` | 重新下载并复位；本工程设为Reset & Run，随后运行 | 需要烧入新程序时，事先保持急停与驱动力隔离 |
| `Attach to Running Program` | 连接程序，不主动下载/复位，也不负责把已暂停的CPU恢复运行 | 已确认固件匹配且CPU为Running，只需实时观察时 |
| `Attach & Halt Program` | 连接并暂停CPU，不下载新固件 | 驱动力已可靠隔离，需要静态检查时 |

**打开ELF ≠ 下载ELF；Attach ≠ 烧录；已连接 ≠ CPU正在运行。** Attach前必须确认当前板上程序就是这份ELF对应的版本，
否则变量地址/类型可能错，读数也不可信。

先由队员隔离驱动力后再做诊断。隔离可能造成电机离线/CAN故障，此时Dead可能正常，不能伪装成正常带电运行状态。
**任何工具里都不能带运动指令暂停、单步或打断点。** CPU停住后不再发送新控制帧，电机可能保持旧指令；
调试设置还可能冻结IWDG，因此不能指望“停住后看门狗会救场”。也不要在运动中写变量强制进入Working。

### 10.2 打开变量窗口，一步步找到对象

1. 调试器拔掉后不能读取实时变量，旧窗口数值可能只是缓存。按现场规程隔离驱动力、断电接回探针后，恢复供电并打开本板`.jdebug`；按上表连接。普通实时诊断用Attach to Running Program，不要用Halt凑读数。
2. 从`View`打开`Global Data`和`Watched Data`窗口（有些版本在View的子菜单中）。新工程已预填uwTick、g_reset_by_iwdg、g_cpu整体结构、合法/非法DBUS计数5项；展开g_cpu才有cycle_count，Ctrl+J直接搜cycle_count不保证找到；连上后选字段右键Refresh Rate开启实时刷新。
3. 点`Find → Find Global Data`，或`Ctrl+J`，搜索`s_robot`。选择属于`GetRobot()`的那个静态对象。
4. 展开对象左边的箭头，在成员行右键选`Watch`，把下表关键字段加入`Watched Data`。
5. 同样搜索`s_imu`（属于`GetImu()`）和`s_comm`（属于`GetGimbalChassisComm()`），展开需要的成员。
6. 这些是实际存在的静态对象，不需要输入`GetRobot()`、`GetImu()`或`setInput()`来执行芯片函数。
   各版本可能显示为`GetRobot()::s_robot`等限定名；表中写的是对象和成员，不要求把GDB的`$r`表达式粘进Ozone。
7. 如果全局搜索未显示静态对象，打开本板`Instance/component/ins_robot.cpp`，定位`GetRobot()`内的`s_robot`声明，右键Watch；
   也可搜索编译符号列表。仍找不到时，先核对程序文件和调试信息，不捏造地址或改状态机。

| 从哪个对象展开 | 先看字段 | 怎么理解 |
|---|---|---|
| `s_robot` | `state_` | 0=Dead，1=恢复自检，2=Working；Working仍不等于已解除急停 |
| `s_robot` | `estop_` | true=急停，先保持它为真完成起动确认 |
| `s_robot` | `can_tx_guard_.faulted_` | true=CAN故障锁存；正常档不能自动清除 |
| 底盘`s_robot` | `remote_armed_`、`mode_` | 前者为上电/故障后急停确认；mode 0分离、1跟随、2小陀螺；云台没有这两个字段 |
| `s_robot` | `remote_input_` | 本周期遥控快照；left/right原始档值1上、3中、2下，轴值已过死区 |
| `s_robot` | `rc_checker_`、`motor_checkers_` | 当前遥控来源必须在线；云台接收时底盘rc_checker_离线可正常，改看remote_source_与comm_内remote_relay_；电机仍须全部在线 |
| `s_imu` | `error_state_`、`inited_`、`samples_`、`calibrated_` | 初始化错误、有效样本累计、标定是否完成 |
| `s_imu` | `sample_valid_`、`healthy_`及`last_sample_tick_` | 当次有效、长期健康是不同条件；还需与uwTick核对样本/时钟/DRDY是否超过20ms，原始缓存布尔值不会自动随时间改变 |
| `s_imu` | `last_clock_tick_`、`last_accel_tick_`、`last_gyro_tick_` | 设备时钟和两传感器新鲜度时间戳；与uwTick比较，不能单用“角度没变”判冻结 |
| `s_comm` | `received_`、`last_rx_tick_`、`chassis_data_`、`gimbal_data_` | 是否收过对板帧、最后接收时间、双板命令与就绪状态 |
| 全局 | `g_reset_by_iwdg` | 本次启动是否由独立看门狗复位，不能只靠调试器掉线判断 |
| 全局 | `robot::g_fault_injection_enabled` | 正常三模式固件应为false；nm查到符号不能证明它为false |
| 全局 | `robot::diag::g_cpu` | 周期最大值与超时计数，84tick约1μs；重点看max和overrun |

本轮已对两板ELF检查对象符号与上述字段。**Ozone界面中的解析、实时刷新和芯片实际读数仍需现场验证**；
没有把GDB离线解析成功当成Ozone上板验证通过。

### 10.3 实时观察与波形

在队员确认的受控台架条件下，先确认程序为Running、周期计数持续增长，再用`Attach to Running Program`连接观察，避免为看状态主动暂停。
在`Watched Data`的字段行右键，设置`Refresh Rate`，先只对少量关键字段选低刷新率（例如5 Hz，若该版本提供）。
本工程关闭`VAR_ALLOW_BMA_EMULATION`，避免探针通过“短暂停CPU”模拟后台读取；目标不支持后台读取时，停止实时观测并交队员处理，不能改成反复halt采样。

需要趋势时，可在数据行右键`Graph`加入`Data Sampling`，少量低频观察即可；普通PC采样不是严格同步快照，
也不能用5 Hz曲线证明1ms保护时序。精确急停、卸力时间仍按docs/08用对应测量设备验证。

如果为比较拨杆使用静态暂停读数，CPU暂停时遥控解码也暂停，拨杆动了变量不会自动更新。
保持驱动力隔离，由队员Continue运行采样，再Halt读取；禁止在实际运动中这样操作。
调试结束后结束会话、断电；再测试三模式时回第4节正常上电，不在暂停位置直接继续试车。

## 11. 现象与可能改动

| 现象 | 先检查 | 确认后可能改什么 |
|---|---|---|
| 全不动 | 授权、烧录、DBUS、全体在线、IMU、CAN锁存 | 硬件确实不同时才改ID/路由/引脚；先不改PID |
| 某轮看着反 | 等效解与实际滚动矢量 | 证实正向错误后才改对应Dir |
| 舵角固定偏一截 | 机械零位与offset | kSteerAngleOffset，不靠Kp纠正零点 |
| 起步猛或自旋太快 | 速度、加速度范围 | 底盘robot.cpp上限；不先加电流 |
| 抖动/来回摆 | 正反馈、卡滞、零点错误 | 方向正确后再调对应PID/跟随增益 |
| 小陀螺松杆仍转 | 模式本来有非零旋转 | 降低最小/最大自旋，停机用急停 |
| pitch快碰结构 | 立即急停，确认行程 | 两处pitch上下限、留余量，两板重编重烧 |
| 掉力、故障码、发热 | 立即停机查供电、堵转、过流/过温 | 达妙故障已禁止自动清错并锁存失能；排根因后由队员断电恢复，不靠加力矩限幅处理 |

完整符号、当前值、联动位置和重烧哪块见`docs/14`。一次只改一组，记录原值、新值和现象，不对就恢复。
