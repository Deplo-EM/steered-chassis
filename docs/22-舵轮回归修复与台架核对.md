# 22 · 舵轮回归修复与台架核对（2026-11-14）

本轮基于 `c73c2b4` 的工作区。修正后的拓扑图优先于旧图、通用接线建议和 DSH 对话中的早期判断。当前只验证分离、跟随、小陀螺和两轴云台。**离线验证已完成；尚未烧录或做台架验证。**

## 1. 为什么之前一只轮子会转，现在却全不转

| 版本或现象 | 代码和记录能证明什么 |
|---|---|
| `7792f63`：现场有一次单轮连续滚动，随后推左杆有对应响应 | 该版按轮放行：只要有一只舵轮达到阈值，这只轮就能得到驱动。该次现象提示至少一路曾有响应，但当时没有同步记录舵角、车体旋转指令或四路电流，无法追认具体驱动命令。 |
| `ef2de36` 起改为四轮一起等待 | 只要有一只参与运动的轮组没到位，四轮驱动电流都会归零。已确认左杆输入变化、舵向发送缓冲区变化；轮组未转、驱动缓冲区为零，与这个门控条件相符。缓冲区非零只证明软件编码出了命令。 |
| `c73c2b4`：300 ms 后改为按轮放行 | 主机复现：同样的指令下恰好一轮对齐，会在超时后重新出现单轮驱动；全部未到位时仍然全零。超时放行不能修复舵机不转。 |
| 本轮 | 按实测舵角选择较短的等效转向路径，并保留换向滞回。凡需参与运动的轮组，都要在目标附近才一起放行；300 ms 只标记超时。若舵角还差 0.35 rad 以上、电压指令幅值至少 8000 raw、同一方向持续 500 ms 都没向目标推进至少 0.04 rad，置故障轮号并撤销输出。右拨杆回下档且其余条件恢复后才可重新准备。 |

`0x206` 说明底盘 CAN1 曾收到一条符合舵电机 ID 2 的反馈；`0x201` 说明底盘 CAN2 曾见到轮电机反馈。它们不能证明某条非零控制命令已上总线或被目标电机执行。没有证据说明现场换线就能解决，也没有证据说明该车已确认打开 GM6020 的电流控制。先用匹配修正图的正常固件采样。

## 2. 当前采用的接线和参数

| 对象 | 修正图与本轮正常固件 |
|---|---|
| DBUS 接收机 | 云台 USART3；原始帧经过完整性校验后由云台转发到底盘。底盘本地串口计数为 0 在该接法下是正常的。 |
| GM6020 舵电机 | 底盘 CAN1，设备 ID 1～4，反馈 `0x205`～`0x208`；按说明书默认电压模式，发 `0x1FF`。 |
| M3508 驱动 | 底盘 CAN2，设备 ID 1～4，反馈 `0x201`～`0x204`，控制帧 `0x200`。 |
| Yaw | 修正图标 DMJ620，ID 1；接在与云台 CAN1 共线的底盘 CAN2 上，由云台程序发送控制。 |
| Pitch | 修正图标 DMJ620，ID 2；接云台 CAN2。 |
| 双板通信 | 底盘 CAN2 ↔ 云台 CAN1。接收与发送统一采用 `board_wiring.hpp`；反馈不能从另一条总线冒充在线。 |

修正图没给达妙型号后缀、MIT 的 P/V/T 量程或实车几何。代码保留现有驱动的协议量程和上一份明确的 6.2 标定（轮半径 0.066 m，轮位 x/y 为 ±0.167 m，M3508 出厂减速约 19.2:1）。DMJ620 标注不能证明这些达妙量程匹配。现场先从队里核对实际型号和已配置的量程，再考虑修正固件；不改电机设置。舵角零点、方向及 PID 也未根据一次现象盲调。

## 3. 到现场先烧两份正常固件

1. 按 [Ozone 图文流程](12-基地现场一页纸.md) 固定车架、架空四轮，确认可立即切断动力。烧录阶段隔离电机动力，板子接到可烧录的逻辑电源；遥控先开、右拨杆下档、各轴回中。底盘用 `debug/ozone/chassis.jdebug`，云台用 `debug/ozone/gimbal.jdebug`。各自下载并校验，运行用 **Reset & Run**。探针还接着时，可以直接看运行数据；要换板才结束当前会话。
2. 两板一起上电后，右拨杆保持下档并等标定。Ozone 用 **Attach** 观察已在运行的板，不设断点。云台 `s_dbus_valid_frames` 应增长；底盘展开 `s_robot`，看 `peer_online_`、`peer_input_.working`、`remote_input_.online`、`remote_armed_`、`motors_online_`、`state_` 和 `can_tx_guard_.faulted_`。若状态未到 `kWorking`，先对照哪一项不满足；不要把 `g_reset_by_iwdg==1` 当作当前仍在重复复位，连着看 `uwTick` 有没有回零。
3. 在 `kWorking` 后，从左上档分离开始，右拨到中档，短时推少量左杆。舵向先转到位，才应有车轮驱动。若无反应或单轮自行持续滚动，先急停，记录现象。异常时留存 `s_chassis.align_pending_ms_`、`align_timeout_`、`align_blocked_mask_`、`steer_stall_mask_`、`alignment_at_stall_`：位 0/1/2/3 对应左前、左后、右后、右前；例如 `0x02` 为左后。急停后实时值会清零，`alignment_at_stall_` 会留到下一次停机锁存或重启。`s_can_tx_fail_count` 统计提交失败，只能辅助定位；未增长不等于电机收到了命令。
4. 四轮转向和驱动正常后，再按左中档跟随、左下档小陀螺顺序验证。换档前先急停；小陀螺解除急停会主动旋转，松开摇杆不会退出。实车确认前不依据 `SAFE-BUILD` 判断车辆已通过安全验收。

## 4. 若有舵向命令却无反馈变化：可用独立的 ID 2 探针

只在固定架空的台架上使用 `debug/ozone/chassis_steer_probe.jdebug`；云台仍用配套的正常固件。探针不走正常舵向发送路径，驱动轮和云台均保持禁止输出，只测试底盘 CAN1 的 GM6020 ID 2。测试完恢复正常底盘固件。

1. 先用电压：左拨杆上档，右拨杆下档，所有轴回中，等待半秒。观察 `robot::probe::g_steer_probe_phase`。
2. 右拨杆移到中档、其余保持回中，等半秒。轻推左杆向前，触发一个不超过 160 ms 的受限脉冲；松杆或拨回急停都停止试探。观察 `robot::probe::g_steer_probe_voltage`。只有队里确认开启电流环时，才考虑用左拨杆中档重复并观察 `g_steer_probe_current`，不要修改电机配置。

| 观察量 | 可以下的结论 |
|---|---|
| `attempted` 为 0 | 没有尝试提交非零脉冲。先看是否完成急停确认、回中和准入。 |
| `attempted` 非零，`queued` 为 0 | 没有进入发送邮箱，查 CAN 提交和保护状态。 |
| `queued` 非零，`sent` 为 0 | 没有得到该脉冲帧的发送完成证据。`unconfirmed` 包括超时、取消或发送未确认。 |
| `sent` 非零 | bxCAN 对对应非零帧报告 TXOK。它可以由同总线其他节点 ACK，不能单独证明 ID 2 执行。 |
| `peak_delta_a`、`peak_angle_rad` 明显变化 | 才能把发送证据与目标电机反馈对照。若仍无变化，先看队里可用版本的帧、反馈新鲜度和控制模式；小脉冲没有克服静摩擦也不能排除。 |
| `completed` 非零 | 试探达到时间或角位移终止条件；不代表发送成功。 |
