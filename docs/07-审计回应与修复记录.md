## 1. 高风险项

### H1 · 看门狗没有监督主控制周期 —— **成立，已修复**

**审计说的是对的**：原来的喂狗写在 UART 接收中断和 CAN 解帧回调里。UART 中断优先级 0、
TIM6 是 3，CAN 接收中断也高于 TIM6。所以哪怕控制循环卡死，这些中断照样会进来喂狗，
看门狗永远等不到复位——"任务卡死 200ms 复位"这条验收项等于没实现。

**修复**：

1. 中断里**只记录**"收到了一帧合法数据"的时间戳与计数，删掉所有 `HAL_IWDG_Refresh`；
2. 每块板只剩**一个**喂狗点：`CommTask()` 的最后一行；
3. `CommTask()` 由 TIM6 在 `MainTask()`（控制、逆解、闭环、下发）之后调用。

于是：控制循环没跑完 → 走不到喂狗 → 200ms 复位。

**证据**（可复核）：

```powershell
# 全仓库只剩两处 HAL_IWDG_Refresh，且都在各自 CommTask 的末尾
Select-String -Path Chassis\**\*.cpp,Gimbal\**\*.cpp -Pattern "HAL_IWDG_Refresh"
# 调用顺序
Select-String -Path Chassis\Task\component\main_task.cpp -Pattern "MainTask\(\)|CommTask\(\)"
```

### H2 · 任意 18 字节都能维持"遥控在线" —— **成立，已修复**

**问题**：`DT7` 只解码、不校验。串口错位、噪声、接收机掉电时的全零数据，只要凑够
18 字节就会被当成有效指令，还会刷新在线时间戳、喂看门狗。

**修复**：新增 `RobotComponents/component/dbus_check.hpp`：

- 5 个模拟通道必须落在 **364~1684**（DBUS 协议的有效范围，中位 1024）；
- 两个拨杆必须 ∈ {1,2,3}（0 是非法值，不能当成"没急停"）；
- 非法帧：**不解码、不刷新在线时间戳、不喂狗**。

**证据**：新增 6 个测试用例（合法帧、全零帧、通道越界、拨杆为 0、拨杆 2/3、边界值），
`tests/run_tests.ps1` 从 112 项增加到 **157 项，全部通过**。

### H3 · 未进入 Working 时舵机仍动作 —— **成立，已修复**

**审计引用了说明书的内部矛盾**：第 3 页红线要求"未进入 Working 所有电机输出归零"，
第 8 页又说 Resurrection 可以"舵向角回中"。两者不能同时满足。

**处理**：按**红线优先**。删除了 `Chassis::centerSteer()` 以及 Resurrection 阶段的调用，
非 Working 状态一律 `setInput(0)`。

> 如果考核方明确要求自检回中，需要在书面确认后做成"受遥控器确认、限速、急停可打断"
> 的流程，而不是现在的无条件动作。

### H4 · 急停零帧没有送达保证 —— **部分修复，剩余风险已文档化**

**已修复**：

- `CAN_Send_Msg()` 改为返回 `bool`（`HAL_CAN_AddTxMessage` 的结果），两板调用处都检查；
- 失败次数累加（`s_can_tx_fail_count`），验收时可以观察它是否为 0；
- 接收侧补了 `RTR == CAN_RTR_DATA && DLC == 8` 的校验。

**仍未解决**（需要硬件/配置层面配合，代码改不动）：

1. **总线 bus-off**：`can.c` 里 `AutoBusOff = DISABLE`，总线被打死之后外设不会自恢复，
   此时任何帧都发不出去。这属于 CubeMX 生成代码，按规定不手改；建议在 `.ioc` 里打开
   AutoBusOff，或验收前用**硬件急停**兜底。
2. **达妙自身超时**：达妙是"不收到新指令就保持上一帧"，建议在上位机把它的 TIMEOUT
   设成 50~100ms，这样即使 CAN 全断，电机也会自己错误停机。

## 2. 中风险项

### M1 · 坐标变换口径与 PDF 不一致 —— **保持代码，文档写明**

审计的判断和我一致：PDF 3.2 的公式与它自己"δ = 云台朝向 − 车头朝向"的定义差一个符号；
按物理描述（枪口左偏 90°、推前进应向左走），代码用的 R(+δ) 是对的。

**处理**：不改代码（改了会变成物理错误），但在 `chassis_ik_solver.cpp` 和
`docs/01` 里写清了推导、检验方法、以及**如果实车方向不对该改哪一行**。
验收前建议与考核方书面确认一次符号约定。

### M2 · 接收机接线声明不一致 —— **成立（文档错误），已修复**

README 曾写"接收机在云台板时底盘也能工作"，但底盘进 Working 必须本板 DBUS 在线，
对端 `dbus_online` 只用于喂狗。已改为明确表述：

> 底盘板**必须**自己的 USART3 接 DBUS；云台帧里的 `dbus_online` 只保活，不提供摇杆数据。

### M3 · 运行期传感器健康无闭环 —— **成立，已修复**

新增 `Imu::isHealthy()`：每周期检查数据是否有限、加速度模长是否在 `[2, 40] m/s²`、
角速度是否 `< 50 rad/s`；连续 50 个采样异常即判失效。两板状态机都改成：

```cpp
imu_ok = imu_->isCalibrated() && imu_->isHealthy();
```

传感器中途坏掉 → 回 Dead → 输出归零。

### M4 · 报文合法性不完整 —— **成立，已修复**

- 接收回调检查 `IDE / RTR / DLC`；
- 双板协议 `decode()` 改为返回 `bool`，CRC 错误返回 `false` 并计数；
- 电机 `decode()` 的返回值决定是否 `notifyMotorRx()`（不再"解包失败也算在线"）；
- 云台板解 C2G 处**不再喂狗**（H1 的同一处修复）。

**证据**：新增"CRC 错误时 decode 必须返回 false"与"正常帧返回 true 并计数"两个用例。

### M5 · 并发快照缺失 —— **部分成立，接受并记录**

控制循环（TIM6）读取中断写入的 `GimbalData` / `ChassisData`，理论上可能读到跨两帧的混合值。

**为什么暂不做双缓冲**：

- 每块板每秒 1000 帧，跨帧偏斜最多 1ms；
- 受影响的是 `yaw_joint`（物理时间常数远大于 1ms）和几个布尔标志；
- 引入双缓冲 + 临界区本身也会带来新的并发 bug 风险，收益/风险比不划算。

**已做的缓解**：所有字段都是 1~4 字节的独立写入，不会出现"半个 float"；
`decode()` 先校验 CRC 再逐字段写，坏帧不会写。

若后续要彻底解决，建议做法：`decode()` 写入影子结构体 → 原子翻转一个索引 →
控制循环在临界区里整体拷贝一次。

### M6 · 实车参数未标定 —— **成立，本来就是"待上车"清单**

已在 `docs/00` 第 3 节列出全部待标定项（电机方向、舵角零点、IMU 片选/安装方向、
达妙零位、PID 增益、几何尺寸），并在 `docs/06` 给出逐步标定方法。

## 4.5 第二轮复核（2026-10-20）：F1 / F2 / F3

审计对上面这份修复记录又做了一次独立复核（`../../audit_followup_2026-10-20.md`），
抓到一个**我在修复 H2 时引入的新漏洞**。逐条处理：

### F1 · 拨轮位宽不一致，H2 仍可绕过 —— **成立，已修复**

**问题**：我的校验器把拨轮按 11 位取（`& 0x07FF`），但 DT7 解码器是把 16 位整体当整数用
（`tmp = data[16] | (data[17] << 8)`）。于是 `data[16..17] = 0xFC00` 时：

- 校验器看到低 11 位 = 1024 → **判合法**；
- 解码器算出 `(0xFC00 − 1024)/660 ≈ 96.19` → 远超 [-1, 1]；
- 分离模式里 `w = 96.19 × 6 ≈ 577 rad/s`，而且原来的加速度斜坡**只限变化率、不限幅值**。

**修复**：

1. `DbusChannel()` 的拨轮分支改为返回**完整 16 位**，与解码器读同一个宽度
   （`dbus_check.hpp` 里有注释说明为什么不能掩 11 位）；
2. 摇杆值在使用前统一 `UnitClamp` 到 [-1, 1]；
3. 目标 `(vx, vy, w)` 在进入斜坡前**再兜底钳位**一次（独立于分支逻辑的防线）。

**证据**（先红后绿）：

```
修复前：163 项检查，失败 2 项（`DbusChannel(frame,4) == 0xFC00` 失败、非法帧未被拒绝）
修复后：163 项检查，0 失败；再把 DT7 解码器编进测试做「校验-解码对拍」后共 **171 项**
```

用例覆盖：拨轮 0xFC00、1690、200、正常 1024，以及"拨轮按 16 位参与范围检查"。

### F2 · 看门狗验收说明写反 —— **成立，已修复**

**问题**：原文档说"把 `kWatchdogFeedEnable` 改 false 重烧，板子不复位"。
实际代码是 `if (kWatchdogFeedEnable && ...) feed;`，改 false = **停止喂狗** = 板子一直复位，
和文档承诺正好相反；拿它做"反证实验"当然也做不成。

**修复**：

1. 语义改成正向的 `kDebugAlwaysFeedWatchdog`（**默认 false = 正常条件喂狗**；
   `true` = 调试模式无条件喂狗，板子不复位）；
2. 增加**复位原因记录**：`MainTaskInit()` 开头读 `RCC_FLAG_IWDGRST` 并清标志，
   存进全局 `g_reset_by_iwdg`。验收时关遥控器 → 复位 → 连调试器读它 = true，
   直接证明"这次是看门狗复位"，比看 LED 可靠（审计建议的做法）；
3. README、`docs/00`、`docs/06` 三处验收步骤全部改写，并标注"方向别搞反"。

### F3 · 运行期 IMU 保护仍然有限 —— **成立，已改进（仍不完整）**

**已改**：

- 坏样本**不再进入**标定和 Mahony（原来先喂再判），避免一次坏数据把姿态拉歪；
- 恢复健康要求**连续 100 个正常采样**（原来一次正常采样就恢复），并保留 50 个异常
  采样判定失效；
- 局限（读数冻结在物理上合理的旧值）**无法**在本层检测，因为 `BMI088.cpp` 丢弃了
  `HAL_SPI_*` 的返回值。要彻底解决必须改芯片驱动上报 SPI 状态，已在代码注释和本文档
  中明确记录，未做隐瞒。

### F2 附带的文档矛盾

`docs/00` 第 5 节第 5 条原来写"两板 DBUS 可在接收机接哪块板上容错"，与 README
"底盘必须本地 DBUS"矛盾。已改为："两板都实现解码是任务要求，但控制上不容错"。

## 5. 仍未验证、需要台架做的事（诚实清单）

审计说得对：静态审查 + 编译 + 主机测试**不能**替代故障注入。以下必须在车上做：

1. **注入 TIM6 卡死**（例如在 `MainTask` 里加死循环），确认 200ms 内复位；
2. **注入非法 DBUS**（拔掉接收机、短接 RX 制造噪声、构造 0xFC00 拨轮帧），确认车不动；
3. **测量 1ms 周期的最坏执行时间**（SPI 读 IMU 是主要开销），确认没有超时；
4. **CAN 发送失败计数**在正常运行时是否恒为 0；
5. **急停响应时间**用逻辑分析仪量一次（从拨杆到位到零帧上总线）；
6. **SPI 断续/读数冻结**的注入测试（F3 的残留风险）。
